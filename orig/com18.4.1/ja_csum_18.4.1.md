### Условия применения

Компонент «ja_CSum» может использоваться с СУБД «Jatoba» версий 4.x и выше, под управлением операционной системы GNU/Linux.

![](@site/docs/assets/images/com18.3.1/ja_csum_tmp/media/image2.png)

«Jatoba data safe».

Ограничений по совместимости с другими компонентами нет.

## УСТАНОВКА И НАСТРОЙКА

Установка компонента «ja_CSum» должна производится от имени пользователя, обладающего административными привилегиями в операционной системе. Данный компонент штатным образом может быть установлен только с СУБД «Jatoba» (см. документ «Защищенная система управления базами данных «Jatoba». Руководство по установке).

### Установка компонента «ja_CSum» в ОС GNU/Linux

Компонент устанавливается в составе СУБД «Jatoba». Его возможно установить при первичной установке либо доустановить.

Установку компонента возможно провести двумя способами:

1)  установка из локального репозитория (CDROM) – производится из файлов, записанных на компакт-диск или скопированных с него;

2)  установка непосредственно из deb/rpm-файлов – производится опционально, по усмотрению пользователя.

Компонент выполнен в виде отдельного deb или rpm-пакета. Установка компонента осуществляется средствами пакетного менеджера ОС. Для разных типов пакетных менеджеров команда установки немного отличается. Ниже приведены основные типы:

- для систем на основе пакетного менеджера APT (к таким системам относятся все ОС семейства Debian, использующие deb-пакеты) команда установки следующая:

```
# apt-get install jatoba<ver>-ja-csum
```

- для систем на основе пакетных менеджеров YUM/DNF (к таким системам относятся все ОС семейства RedHat и вышедшие из нее, использующие rpm-пакеты) команда установки следующая:

```
# yum install jatoba<ver>-ja_csum \# dnf install jatoba<ver>-ja_csum
```

Отдельного уточнения требуют операционные системы ALT Linux и openSUSE.

- ALT Linux использует пакетный менеджер APT, но распространяется в виде rpm-пакетов и для нее команда установки выглядит аналогично Debian:

```
# apt-get install jatoba<ver>-ja_csum
```

Установка компонента в составе других версий СУБД «Jatoba» осуществляется аналогично. Отличие будет только в номере версии СУБД, в составе которой он распространяется. Например, jatoba4-ja_csum и т.п.

Удаление модуля также осуществляется средствами пакетного менеджера ОС. Вместо команды install нужно использовать соответствующую данному пакетному менеджеру команду удаления (remove, purge, erase и т.п.).

Для получения детальной информации по пакетному менеджеру рекомендуется обратиться к документации по ОС.

### Настройка конфигурационного файла «postgresql.conf»

Для осуществления контроля целостности (расчета контрольных сумм, далее КС) программного обеспечения и выполнения меры защиты информации ОЦЛ.1 потребуется в конфигурационном файле «postgresql.conf» установить параметры регистрации событий в СУБД.

Файл расположен в каталоге:

/var/lib/jatoba/<ver>/data/

В нем в разделе «REPORTING AND LOGGING» рекомендуется проверить наличие активных параметров:

log_destination = 'csvlog' logging_collector = on log_directory = 'log'

Для передачи событий безопасности средствами компонента «ja_Log» в пользовательский веб-интерфейс для администраторов «Jatoba data safe», параметр

«log_destination» рекомендуется установить на формирование файлов в формате \*.csv.

Уровень детализации сообщений в параметре «log_min_messages» должен быть установлен не ниже параметра «warning», а рекомендованный параметр – «info»:

log_min_messages = info

### Установка расширения «ja_csum»

Установка расширения «ja_csum» выполняется автоматически при первом старте СУБД. Для чего достаточно:

– в разделе «Shared Library Preloading» для последующей загрузки расширения установить параметр:

shared_preload_libraries = 'ja_csum'

– в разделе «CUSTOMIZED OPTIONS» для установки расширения в БД установить параметр:

![](@site/docs/assets/images/com18.3.1/ja_csum_tmp/media/image6.png)

ja_csum.db_name = 'postgres'

Рисунок 2.4 – Параметр установки расширения «ja_csum» в БД

![](@site/docs/assets/images/com18.3.1/ja_csum_tmp/media/image1.png)

В случае, если расширение ja_csum не было установлено в БД, заданную в параметре ja_csum.db_name, то в журнал работы СУБД записывается сообщение:

extension ja_csum is not installed

– в разделе «CUSTOMIZED OPTIONS» определить файловый каталог, в котором будет храниться файл контрольных сумм через параметр (определяется через параметр **ja_csum.work_dir**):

ja_csum.work_dir = '/var/lib/jatoba/18/data/ja_csum'

Если параметр ja_csum.work_dir явно не задан, то при установке расширения ja_csum он будет создан внутри каталога PGDATA, например,

![](@site/docs/assets/images/com18.3.1/ja_csum_tmp/media/image1.png)

Каталог с файлами контрольных сумм, указанный в параметре ja_csum.work_dir, должен находиться внутри каталога данных СУБД - **PGDATA**.

При ручном создании каталога с файлами контрольных сумм пользователь ОС **postgres** должен иметь на него права доступа «0700». В ином случае создание каталога прерывается, а в журнал работы СУБД записывается сообщение:

can't create directory \[ja_csum.work_dir_name\] specified in parameter ja_csum.work_dir: \[mkdir_error\]

В случае, если каталог, указанный в параметре ja_csum.work_dir, не расположен внутри каталога PGDATA, то в журнал работы СУБД будет выведено сообщение:

the directory <work_dir> specified in parameter ja_csum.work_dir must be inside PGDATA

![](@site/docs/assets/images/com18.3.1/ja_csum_tmp/media/image1.png)

В случае, если каталог, заданный параметром ja_csum.work_dir не может быть создан, то в журнал работы СУБД будет выведено сообщение

can't create directory <work_dir> specified in parameter ja_csum.work_dir: ошибка

– в разделе «CUSTOMIZED OPTIONS» определить автоматическую установку расширения в БД (определяется через параметр **ja_csum.db_name**):

ja_csum.auto_create_extension = on

## ФУНКЦИОНАЛЬНЫЕ ВОЗМОЖНОСТИ КОМПОНЕНТА

Компонент «ja_CSum» служит для выполнения контроля целостности файлов СУБД и БД, а также для ограничения программной среды в СУБД.

Для выполнения блокировки пользователей СУБД и БД используется дополнительный компонент «SecurityProfile», входящий в состав СУБД «Jatoba».

Обязательные контролируемые объекты БД:

- процедуры и функции, написанные на языках C, SQL, plpgsql и других;

- агрегатные функции;

- триггеры на таблицы и представления;

- триггеры на события;

- представления;

- материализованные представления;

- пользовательские типы (композитные, перечисления, диапазоны).

Обязательные контролируемые объекты СУБД:

- «postgresql.conf» – главный конфигурационный файл СУБД;

- «pg_hba.conf» – конфигурационный файл правил аутентификации в СУБД;

- «pg_ident.conf» – конфигурационный файл сопоставлений имен пользователей для правил аутентификации в СУБД;

- «postgresql.auto.conf» – конфигурационный файл, хранящий изменения, вносимые в конфигурацию СУБД через SQL-команду «ALTER SYSTEM».

В компоненте «ja_CSum» предопределены перечни, которые запрещены для изменения:

- стандартных расширения PostgreSQL (см. [Приложение 2](#_bookmark60));

- компонентов, входящих в комплект поставки (см. [Приложение 1](#_bookmark62)).

Рекомендуется после загрузки расширений пересоздать файлы контрольных сумм,

вызвав функцию **select ja_csum.fill_list()**, как описано в п. [3.2](#расчет-кс-файлов-субд-ja_csum.fill_list) настоящего документа, т.к. в ходе установки расширения будут добавлены новые данные (таблицы, схемы, функции и т.д.). Новые объекты должны быть поставлены на контроль, чтобы исключить срабатывания механизма блокировки пользователей в СУБД.

### Установка периодичности проверки (ja_csum.check_interval)

В соответствии с «Требованиями по безопасности информации к системам управления базами данных (выписка)», утвержденными Приказом ФСТЭК России № 64 от 14.04.2023, контроль целостности СУБД должен проводится не менее 1 раза в сутки. Для выполнения данного требования по умолчанию установлен параметр «1440» минут, что соответствует количеству минут в сутках.

Соответственно отсчет времени начнется с момента первой проверки.

![](@site/docs/assets/images/com18.3.1/ja_csum_tmp/media/image16.png)

Рисунок 3.5 – Проверка установленного интервала проверки Периодичность проверки контрольных сумм устанавливается SQL-командой:

ALTER SYSTEM SET ja_csum.check_interval = <number of minutes>;

Параметр интервала проверок может быть установлен в диапазоне от 1 до 35 000 минут. Отрицательные и дробные значения не допускаются.

При установке параметра:

- выполнится внеочередная проверка;

- компонент запомнит время выполнения проверки;

- время выполнения последующих проверок будет отсчитываться от времени выполнения SQL-команды, т.е. от времени установки параметра «ja_csum.check_interval».

Например

Для установки периодичности проверки КЦ раз в 2880 минут выполняется SQL-команда:

ALTER SYSTEM SET ja_csum.check_interval = 2880;

После чего выполняется проверка установленного параметра SQL-командой:

![](@site/docs/assets/images/com18.3.1/ja_csum_tmp/media/image17.png)

### Режим информирования «permissive»

Режим информирования «permissive» может использоваться при вводе СУБД в эксплуатацию, когда окончательно не сформировался список используемых расширений и настроек СУБД.

Получаемые сообщения от компонента в журнале событий, позволят администратору СУБД проанализировать их, окончательно настроить СУБД и минимизировать риск нарушения контроля целостности с последующей блокировкой пользователей.

В данном режиме блокировка пользователей не осуществляется.

Установка режима информирования «permissive» выполняется SQL-командой:

![](@site/docs/assets/images/com18.3.1/ja_csum_tmp/media/image24.png)

### Режим блокирования «enforcing»

Режим блокирования «enforcing» применяется для постоянной работы СУБД для выполнения "Требований по безопасности информации к системам управления базами данных (выписка)», утвержденных Приказом ФСТЭК России № 64 от 14.04.2023 касающихся:

- контроля целостности;

- ограничения программной среды.

Изменения в конфигурацию СУБД и в режим работы пользователей должны быть санкционированы администратором СУБД.

Включение режима блокировки целесообразно при совместной работе компонентов

«ja_CSum» и «securityprofile».

Компонент «ja_CSum» выполняет контроль целостности, а при выявленных нарушениях вызывает компонент «securityprofile» для блокирования пользователей. Ограничение программной среды компонентом выполняется путем:

- разрешения или запрета установки расширений из списка, разрешенного ПО;

- запрета установки расширений, не входящих в список разрешенного ПО.

Компонент «securityprofile» ограничивает программную среду СУБД, перехватывая выполнение команд CREATE FUNCTION / CREATE PROCEDURE.

Установка режима блокирования «enforcing» выполняется SQL-командой:

![](@site/docs/assets/images/com18.3.1/ja_csum_tmp/media/image25.png)

ALTER SYSTEM SET ja_csum.action_mode = 'enforcing';

Рисунок 3.14 – Включение режима блокирования «enforcing»

ALTER SYSTEM SET securityprofile.user_function_creation=off;

### Ограничения на одновременный запуск создания/перерасчета и проверки КС

В компоненте «ja_CSum» применяется ограничение на одновременный запуск функций создания/перерасчета (fill_list()) и проверки (check_now()) файлов КС. Также ограничению подвергаются одновременные запуски нескольких указанных функций.

В случае, если уже выполняется одна из указанных функций, то новая запускаемая функция прерывается, а в журнал событий СУБД выводится сообщение:

ja_csum \* \[started_function\] event \* the function \[running_function\] is already running. please wait until the function completes

Где \[started_function\] – название запускаемой функции, а \[running_function\] – функция, выполняемая в данный момент.

Пример сообщения в журнале событий СУБД:

ja_csum \* fill_list event \* the function check_now is already running. please wait until the function completes

Данные ограничения также могут возникать в том случае, если администратор СУБД запускает вручную одну из функций создания/перерасчета и проверки КС параллельно с уже автоматически запущенными.

### Резервное копирование файлов конфигурации при расчёте КС

В процессе выполнения функции ja_csum.fill_list() расширение ja_csum для каждого файла, перечисленного в таблице param_conf, создаёт его резервную копию в специализированной директории внутри каталога, заданного параметром ja_csum.work_dir (см. п. [3.2.1](#структура-служебного-каталога-и-формат-файлов-эталонных-кс)). Это позволяет администратору при необходимости восстановить исходное состояние конфигурационных файлов до последнего успешного перерасчёта КС.

Резервные копии хранятся в следующей структуре каталогов:

<ja_csum.work_dir>/ backup_configfiles/

<id_1>/

<имя_файла_1>

<id_2>/

<имя_файла_2>

...

Поддиректории с именами, соответствующими значениям id записей из таблицы param_conf, создаются отдельно для каждого файла конфигурации. В каждой поддиректории содержится копия файла конфигурации с тем же именем, что и оригинал.

![](@site/docs/assets/images/com18.3.1/ja_csum_tmp/media/image45.png)

Рисунок 3.34 – Структура каталога с резервными копиями конфигурационных файлов из таблицы param_conf и права доступа

При каждом вызове функции ja_csum.fill_list() расширение выполняет следующую последовательность операций, связанных с резервным копированием:

- проверка существования директории <work_dir>/backup_configfiles. Если директория отсутствует, она создаётся с правами доступа 0700 для системного пользователя postgres. Если права не соответствуют, то расчет КС продолжается, но в журнал записывается предупреждение:

ja_csum \* fill_list_event \* the user postgres does not have the necessary rights to the directory <work_dir>/backup_configfiles

Если при создании директории возникает ошибка, в журнал записывается сообщение:

ja_csum \* fill_list_event \* error while creating the directory

<work_dir>/backup_configfiles

Расчёт КС при этом продолжается.

- аналогично для каждой записи из param_conf выполняется проверка создания и прав доступа к поддиректории <work_dir>/backup_configfiles/<id>;

- если все предыдущие проверки пройдены, файл конфигурации копируется в поддиректорию <id> с замещением существующего файла (то есть каждый перерасчёт КС обновляет резервную копию). Если в процессе копирования возникает ошибка (например, недоступность исходного файла, ошибка записи), в журнал записывается сообщение:

ja_csum \* fill_list_event \* error while backing up the file

<путь_и_имя_файла> to directory

<work_dir>/backup_configfiles/<id>

Все операции резервного копирования выполняются после расчёта КС каждого файла, но до сохранения результатов в файл «fs_checksums_<hostname>_<port>.csv». Таким образом, резервные копии соответствуют состоянию файлов на момент перерасчёта КС.

Для синхронизации структуры каталогов резервных копий с текущим содержимым таблицы param_conf применяется функция **ja_csum.cleanup_backup_configfiles().** Данная функция предназначена для удаления всех поддиректорий внутри

<work_dir>/backup_configfiles/, имена которых являются числовыми значениями и которые отсутствуют в таблице param_conf в виде записей с соответствующим id.

![](@site/docs/assets/images/com18.3.1/ja_csum_tmp/media/image1.png)

Функция ja_csum.cleanup_backup_configfiles() предназначена для ручного вызова администратором после удаления записей из param_conf (например, через delete_param_conf или DELETE), чтобы очистить файловую систему от устаревших резервных копий.

![](@site/docs/assets/images/com18.3.1/ja_csum_tmp/media/image1.png)

### Журналирование событий изменения конфигурационных файлов

В процессе проверки КС конфигурационных файлов, выполняемой функцией ja_csum.check_now(), компонент «ja_CSum» не только выявляет факт изменения файла, но и формирует детализированные события о различиях между текущим содержимым файла и его резервной копией. Это позволяет администратору оперативно отслеживать, какие именно строки были добавлены, удалены или изменены, а также принимать меры в соответствии с политикой безопасности.

При вызове check_now() в первую очередь выполняется проверка файла fs_checksums_<hostname>_<port>.csv, расположенного в каталоге, указанном параметром ja_csum.work_dir (см. п. [3.2.1](#структура-служебного-каталога-и-формат-файлов-эталонных-кс)). При успешном прохождении проверки выполняется расчет текущих КС для всех файлов, перечисленных в таблице param_conf, и сравнение их с сохранёнными значениями из CSV-файла.

Для выявления конкретных изменений используется метод построчного сравнения файлов. Этот метод даёт наглядное представление о различиях, особенно в случае, когда структура файла не предполагает частых вставок/удалений в середине. Рекомендуется избегать произвольного удаления строк в конфигурационных файлах, чтобы минимизировать число ложных срабатываний при сравнении.

После каждого обнаруженного различия компонент «ja_CSum» записывает сообщение в журнал с уровнем WARNING.

В расширении ja_csum определены следующие параметры, влияющие на процесс формирования событий:

- ja_csum.log_format (значения 'standard', 'ja_seceventlog1', по умолчанию 'standard');

Параметр ja_csum.log_format определяет при записи в журнал формат сообщений об изменениях в конфигурационных файлах. При значении 'standard' сообщения записываются в журнал в кратком виде. При значении 'ja_seceventlog1' дополнительно формируются структурированные записи для интеграции с компонентом «ja_seceventlog».

- ja_csum.max_config_event (значения от 1 до максимального целого, по умолчанию 1).

![](@site/docs/assets/images/com18.3.1/ja_csum_tmp/media/image1.png)

Формат записи в журнал зависит от значения параметра ja_csum.log_format:

- если **log_format = 'standard'** (значение по умолчанию), сообщение имеет вид:

ja_csum \* check_now_event \* changes are detected in file %s, line %d

- если **log_format = 'ja_seceventlog1'**, помимо стандартного сообщения, в журнал записывается структурированное сообщение в формате, совместимом с расширением ja_seceventlog:

{

"secEventFileNameConfig":"<полный путь и название изменённого файла>",

"secEventFileNameConfigBackup":"<work_dir>/backup_configfiles/< id>/<имя файла>",

"secEventParameterStringOld":"<значение строки из резервной копии>",

"secEventParameterStringNew":"<значение строки из текущего файла>",

"secEventFileConfigLine":<номер строки в текущем файле>,

"secEventFileConfigBackupLine":<номер строки в резервной копии>

}

Формат ja_seceventlog1 используется только при обнаружении изменений (несовпадении КС). В случае успешной проверки (все КС совпадают) записи в этом формате не создаются – в журнал попадают только стандартные сообщения о завершении работы check_now().

## ДЕЙСТВИЯ АДМИНИСТРАТОРА СУБД ПРИ ИЗМЕНЕНИИ ЦЕЛОСТНОСТИ СУБД

Установленные компоненты «ja_CSum» и «SecurityProfile» при нарушении контроля целостности и ограничения программной среды СУБД в соответствии с "Требованиями по безопасности информации к системам управления базами данных (выписка)» заблокируют пользователей СУБД, что в условиях промышленной эксплуатации СУБД является негативным последствием.

Чтобы избежать негативных последствий выполните последовательность действий, приведенную ниже.

Например, требуется внести санкционированные изменения в конфигурационные файлы СУБД. Порядок действий должен быть следующим:

1)  Перевести компонент «ja_CSum» в режим информирования «permissive» (см. п. [3.7.1](#режим-информирования-permissive)).

2)  Отключить режим периодической проверки (см. п. [3.5](#включениеотключение-режима-периодической-проверки-ja_csum.check_auto)).

3)  Внести требуемые изменения.

4)  Обновить файлы с контрольными суммами (см. п. [3.2](#расчет-кс-файлов-субд-ja_csum.fill_list)).

5)  Перезагрузить СУБД.

6)  Войти в СУБД от имени и с правами Администратора СУБД.

7)  Перевести компонент «ja_CSum» в режим блокирования «enforcing» (см. п. [3.7.2](#режим-блокирования-enforcing)).

8)  Включить режим периодической проверки (см. п. [3.5](#включениеотключение-режима-периодической-проверки-ja_csum.check_auto)).

Для контроля над работой компонентов «ja_CSum», «SecurityProfile» и в целом СУБД, целесообразно воспользоваться функциональными возможностями раздела «Уведомления» (Notifications) компонента пользовательского веб-интерфейса для администраторов «Jatoba data safe».

### Особенности запуска расчета и/или проверки КС на узлах отказоустойчивого кластера «jaDog»

При запуске процедур расчета КС файлов и/или их проверки при совместной эксплуатации с компонентом «jaDog» выполняется определение какая роль узла (главный

1)  Расчет КС файлов СУБД на главном узле кластера.

Выполнение функции fill_list() на главном узле кластера производится для всех объектов СУБД (перечислены в разделе [3](#функциональные-возможности-компонента)). Запись файлов с рассчитанными КС конфигурационных файлов СУБД при этом производится в каталог, указанный в параметре ja_csum.work_dir (см. п. [2.3](#установка-расширения-ja_csum)).

Расчет КС бинарных объектов и объектов СУБД производится в служебные таблицы компонента (см. п. [3.2.2](#служебные-таблицы-и-функции-компонента)). В отказоустойчивом кластере компонента «jaDog» данные служебные таблицы автоматически реплицируются с главного узла на резервные.

2)  Расчет КС файлов СУБД на резервном узле кластера.

Выполнение функции fill_list() на резервном узле кластера производится только для конфигурационных файлов СУБД. Запись файлов с рассчитанными КС конфигурационных файлов СУБД производится точно также как и на главном узле кластера.

Расчет КС бинарных объектов и объектов СУБД при выполнении функции fill_list() на резервном узле кластера не производится, так как таблицы, содержание данную информацию, реплицируются на резервный узел с главного.

1)  Подключиться к БД, указанной в параметре ja_csum.db_name конфигурационного файла postgresql.conf, и выполнить удаление служебных функций компонента «ja_CSum» версии 1.1 из всех БД при помощи SQL-команды:

SELECT ja_csum.deinstall();

2)  Удалить из БД расширение ja_csum компонента «ja_CSum» версии 1.1 при помощи SQL-команды:

DROP EXTENSION ja_csum;

3)  Проверить, что расширение успешно удалено из БД:

\dx

Перечень установленных расширений не должен содержать названия «ja_csum».

4)  Выполнить установку пакета версии 2.х с использованием пакетного менеджера ОС, например, для дистрибутивов с пакетным менеджером APT, команда выглядит следующим образом:

```
# apt-get install ./путь/до/jatoba18-ja-csum_2.1.0-97_amd64.deb
```

5)  В конфигурационном файле postgresql.conf изменить значение параметра ja_csum.work_dir:

ja_csum.work_dir = '/var/lib/jatoba/<ver>/data/ja_csum'

Где <ver> - номер версии установленной СУБД «Jatoba». Каталог «ja_csum» будет создан автоматически. В случае, если каталог уже создан вручную необходимо назначить его владельцем системного пользователя ОС postgres и предоставить права доступа «0700».

6)  В случае, если в составе СУБД эксплуатируется отказоустойчивый кластер

«jaDog» в конфигурационный файл postgresql.conf необходимо добавить дополнительный параметр:

ja_csum.auto_create_extension=off

7)  Убедится в том, что в параметре списка разделяемых библиотек СУБД указано:

shared_preload_libraries = 'ja_csum'

8)  Для первого запуска установить режим информирования:

ja_csum.action_mode = 'permissive'

Подробное описание режимов работы компонента «ja_CSum» приводится в п. [3.7](#режимы-работы-компонента-ja_sum.action_mode).

9)  Сохранить конфигурационный файл postgresql.conf и перезагрузить службу СУБД, а также проверить статус ее работы и наличие ошибок:

```
# systemctl restart jatoba-<ver> && systemctl status jatoba-
```

<ver>

10) Удалить каталог с файлами КС версии 1.1 (по умолчанию использовался

/var/lib/jatoba/ja_csum).

11) Подключиться к БД, указанной в параметре ja_csum.db_name

конфигурационного файла postgresql.conf, и выполнить установку расширения компонента

«ja_CSum»:

CREATE EXTENSION ja_csum;

12) Проверить, что расширение успешно установлено в БД:

\dx

Перечень установленных расширений должен содержать название «ja_csum» и номер версии 2.х.

13) Выполнить перерасчет КС:

SELECT ja_csum.fill_list();

14) Открыть каталог, указанный в параметре ja_csum.work_dir и убедится в том, что в нем успешно созданы файлы с КС (список и формат файлов КС приведен в п. [3.2.1](#структура-служебного-каталога-и-формат-файлов-эталонных-кс)).

15) Выполнить проверку файлов КС:

SELECT ja_csum.check_now();

ALTER SYSTEM SET ja_csum.action_mode = 'enforcing';

17) Перезагрузить службу СУБД, а также проверить статус ее работы и наличие ошибок.

На этом шаге процедура обновления компонента «ja_CSum» до версии 2.х считается завершенной.

### Обновление компонента «ja_CSum» с версии СУБД «Jatoba» J6 до J18

При миграции СУБД «Jatoba» с версии ядра СУБД J6 до J18 обновление компонента

«ja_CSum» с версии 1.1 до 2.х выполняется поэтапно с соответствующими им шагами. **Этап 1. Подготовить СУБД «Jatoba» с версией ядра J6 (исходный кластер) Шаги**

Установить СУБД «Jatoba» с версией ядра J6 (базовая установка) Установить пакет расширения в терминале ОС:

```
# apt-get install jatoba6-ja-csum.
```

В конфигурационном файле «postgresql.conf» (J6) указать строку:

shared_preload_libraries = 'ja_csum'

Запустить и подключиться к СУБД и выполнить SQL-команду в утилите psql:

SELECT ja_csum.check_now();

### Ожидаемый результат

Кластер СУБД «Jatoba» с версией ядра J6 запускается, расширение «ja_csum» загружается через конфигурационный файл (shared_preload_libraries), ручная проверка выполняется без ошибок.

### Возможные ошибки

- Расширение не загружается при старте (ошибка о невозможности загрузить библиотеку) — обычно связано с отсутствующим пакетом или неверным синтаксисом строки «shared_preload_libraries» в конфигурационном файле.

- Функция check_now() возвращает ошибку/не находит объекты расширения —

расширение не установлено/не создано в нужной БД.

### Этап 2. Подготовить СУБД «Jatoba» с версией ядра J18 (целевой кластер) Шаги

Установить СУБД «Jatoba» с версией ядра J18 (базовая установка).

Инициализировать каталог данных СУБД J18 без «data checksums» (для совместимости сценария):

PGSETUP_INITDB_OPTIONS="--no-data-checksums" /usr/jatoba-18/bin/jatoba-setup initdb jatoba-18

Установить пакет расширения в терминале ОС:

```
# apt install jatoba18-ja-csum
```

В конфигурационном файле «postgresql.conf» (J18) указать:

shared_preload_libraries = 'ja_csum'

### Ожидаемый результат

Каталог данных J18 инициализирован, пакет jatoba18-ja-csum установлен, конфигурационный файл готов к запуску с предзагрузкой библиотеки «ja_csum».

### Возможные ошибки

- Ошибки установки пакета (репозиторий/зависимости).

- Некорректный путь/параметры jatoba-setup initdb.

**Этап 3. Подготовить pg_upgrade Шаги**

Остановить обе СУБД J6 и J18.

В СУБД «Jatoba» с версией ядра J6 временно переключить локальную аутентификацию на peer в pg_hba.conf.

### Например

Файл конфигурационном файле аутентификации СУБД

/var/lib/jatoba/6/data/pg_hba.conf Добавить строку:

local all all peer

### Ожидаемый результат

Утилита «pg_upgrade» сможет подключаться локально и выполнить миграцию.

### Возможные ошибки

Утилита «pg_upgrade» не может подключиться к старому/новому кластеру из-за правил pg_hba.conf (ошибка аутентификации).

**Этап 4. Выполнить миграцию утилитой «pg_upgrade» Шаги**

Запустить обновление (без --check) :

/usr/jatoba-18/bin/pg_upgrade -b /usr/jatoba-6/bin -d

/var/lib/jatoba/6/data -B /usr/jatoba-18/bin -D

/var/lib/jatoba/18/data

### Ожидаемый результат

Утилита «pg_upgrade» завершает перенос системных каталогов и данных в целевой каталог J18, формируя обновлённый кластер без дампа/восстановления.

### Возможные ошибки

Несовместимые бинарные файлы/пути -b/-B, неправильные -d/-D, проблемы прав на каталоги данных.

**Этап 5. Первый запуск на новом сервере (критично для ja_CSum) Шаги**

Запустить кластер СУБД «Jatoba» с версией ядра J18 на новом сервере. Сразу после первого старта выполнить команду в нужной БД:

SELECT ja_csum.fill_list();

### Ожидаемый результат

Для нового сервера пересозданы (инициализированы) файлы/списки контрольных сумм «ja_csum», и дальнейшие проверки/фоновая работа расширения выполняются корректно.

### Возможные ошибки

Если пропустить ja_csum.fill_list(), расширение может использовать устаревшее/не валидное состояние контрольных сумм, перенесённое после «pg_upgrade», что приводит к некорректным результатам проверок или ошибкам при обращении к файлам контрольных сумм.

## ТЕРМИНЫ И ОПРЕДЕЛЕНИЯ

**Аутентификационная информация** — информация, используемая при аутентификации субъекта доступа или объекта доступа.

Аутентификация – действия по проверке подлинности субъекта доступа и/или объекта доступа, а также по проверке принадлежности субъекту доступа и/или объекту доступа предъявленного идентификатора доступа и аутентификационной информации (ГОСТ Р 58833-2020).

**Администратор СУБД** – субъект доступа, выполняющий административные функции в СУБД и наделенный правами:

- создавать учетные записи пользователей системы управления базами данных;

- модифицировать, блокировать и удалять учетные записи пользователей системы управления базами данных;

- назначать права доступа пользователям системы управления базами данных к объектам доступа системы управления базами данных;

- управлять конфигурацией системы управления базами данных;

- создавать, подключать базы данных.

Администратор СУБД имеет атрибут SUPERUSER и/или обладает системной учетной записью «postgres».

**Администратор БД** – субъект доступа, выполняющий административные функции в БД и наделенный правами:

- создавать учетные записи пользователей базы данных;

- модифицировать, блокировать и удалять учетные записи пользователей базы данных;

- управлять конфигурацией базы данных;

- назначать права доступа пользователям базы данных (пользователей информационной системы) к объектам доступа базы данных;

- создавать резервные копии базы данных и восстанавливать базу данных из резервной копии;

- создавать, модифицировать и удалять процедуры (программный код), хранимые в базе данных.

Администратор БД имеет атрибут CREATEROLE, и возможные атрибуты BYPASSRLS, REPLICATION, а также прочие системные привилегии относительно БД, кроме атрибута CREATEDB.

**Безусловная блокировка пользователя** – это ограничение пользователя в возможности устанавливать новую сессию с СУБД. Безусловная блокировка имеет приоритет над ограничениями, накладываемыми парольными политикам (блокировка вследствие истечения срока действия пароля, временные блокировки при исчерпании попыток ввода пароля и т.п.), применяется независимо от них и не зависит от применяемого метода аутентификации пользователей. Снятие безусловной блокировки не снимает блокировок по парольным политикам и наоборот.

**Завершение сессии пользователя** – принудительное завершение открытой сессии пользователя с БД/СУБД в заданном режиме.

**Пользователь БД** - субъект доступа, имеющий доступ к ограниченному перечню БД и объектов БД. Имеющий следующий набор привилегий:

- создавать и манипулировать объектами доступа БД (таблица, запись или столбец, поле, представление и иные объекты доступа);

- выполнять процедуры (программный код), хранимые в БД. Пользователь БД имеет обязательный атрибут LOGIN.

**Пользователь СУБД** – см. «Пользователь БД». Для СУБД эти понятия идентичны. СУБД не разграничивает пользователей по отдельным БД. Все пользователи общие, доступ к отдельным БД определяется настройками доступа.

**Режим завершения –** способ завершения открытой сессии пользователя с БД/СУБД работающий в режимах:

- smart – запрещает пользователю выполнение новых транзакций, ожидает завершения текущих транзакций, после этого отключает пользователя;

- fast (режим по умолчанию) – все активные транзакции откатываются, а пользователь принудительно отключается;

- immediate – пользователь принудительно отключается без ожидания и непосредственного отката транзакций

**Роль** – субъект доступа в БД/СУБД, наделенный определенным набором привилегий (чаще всего употребляется как обобщение группы пользователей для выполнения определенного набора действий в БД/СУБД).
