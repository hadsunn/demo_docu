Компонент «SQL_Firewall». Выявление и предотвращение исполнения нетипичных SQL-запросов.

АННОТАЦИЯ

В документе приведены сведения, необходимые для установки и эксплуатации компонента «SQL_Firewall» (далее – компонент или SQL_Firewall). Настоящее руководство предназначено для администратора защищенной системы управления базами данных (СУБД) «Jatoba».

Дополнительная информация

Все примеры в данном документе приведены для СУБД «Jatoba» версии ядра 4.x, для других версий все шаги выполняются аналогично, разница состоит в именах директорий.

Например, СУБД «Jatoba» версии 6.x по умолчанию устанавливается в директорию ОС Linux – «/usr/jatoba-6/bin».

Для СУБД «Jatoba» версии ядра 4 используется версия компонента — 0.8

Для СУБД «Jatoba» версии ядра 5/6/18 используется версия компонента — 1.2

Важная информация

Для сертифицированной версии СУБД «Jatoba» поддерживается работа только на ОС, указанных в формуляре на поставку!

НАЗНАЧЕНИЕ КОМПОНЕНТА​

Компонент «SQL_Firewall» просматривает запросы к СУБД, которые могут быть выполнены, и предотвращает либо предупреждает о выполнении запросов, которые не найдены в установленных правилах («белых списках», WhiteList) по аналогии с брандмауэром, т.е. фильтрует трафик SQL-запросов.

Дополнительная информация

Компонент «SQL_Firewall» не является межсетевым экраном (firewall) в классическом понимании, как программный или программно-аппаратный элемент компьютерной сети, применяемого для фильтрации сетевого трафика.

Компонент «SQL_Firewall» предназначен для защиты базы данных от SQL-инъекций или неожиданных запросов. Входящий запрос перед исполнением подается на обработку в обученную модель машинного обучения, которая возвращает в результате одно значение – вероятность содержания во входящем запросе SQL-инъекции. После этого вычисленная вероятность сравнивается со значением порога классификации, устанавливаемым с помощью параметра СУБД. Запросы с превышенной вероятностью наличия SQL-инъекций прерываются с выводом ошибки.

Условия применения​

Влияние на производительность СУБД​

Применение режима обнаружения SQL-инъекций может приводить к снижению производительности СУБД.

Суммарное влияние компонента «SQL_Firewall» (обнаружение SQL-инъекций + базовые функции фильтрации) на снижение производительности может составлять:

  • в части влияния на TPS - 39,8%, в случае если в белом списке нет запросов из теста и 6,1%, если белый список содержит все запросы теста производительности;

  • в части метрики Latency - 3,14 мс и 0,21 мс, соответственно.

Влияние отдельных компонентов SQL Firewall на снижение производительности в проведенных может составить:

  • в части обнаружения SQL-инъекций - до 6,6% TPS и до 0,31 мс Latency (только для ОС, поддерживающих ML-модель);

  • в части использования базовых функций фильтрации компонента

«SQL_Firewall» (белые списки) - до 38,6% TPS и 3,1 мс Latency, если в белом списке нет запросов из теста и до 1,4% TPS и 0,03 мс Latency, если белый список содержит все запросы теста производительности.

Настройка мониторинга компонента «SQL_Firewall» приведена в документе «Поддержка мониторинга СУБД» 643.72410666.00067-08 98 01-28.

Требования к используемой локали ОС​

При использовании в компоненте SQL Firewall режима обнаружения SQL-инъекций для библиотеки ONNX Runtime (поставляется в составе установочного пакета компонента) в ОС должна быть обеспечена поддержка локали en_US.UTF8. Вывод список доступных локалей в ОС осуществляется при помощи команды:

# locale -a

В случае, если поддержка локали en_US.UTF8 отсутствует в ОС, то необходимо сгенерировать локаль при помощи следующих команд:

# locale-gen en_US
# locale-gen en_US.UTF-8
# update-locale
# update-locale

Необходимо в конфигурационном файле postgresql.conf определить следующие параметры поддержки локали:

lc_messages = 'en_US.UTF-8'
lc_monetary = 'en_US.UTF-8'
lc_numeric = 'en_US.UTF-8'
lc_time = 'en_US.UTF-8'

УСТАНОВКА И НАСТРОЙКА​

Установка компонента должна производиться от имени пользователя, обладающего административными привилегиями в системе. Компонент штатным образом может быть установлен только с СУБД «Jatoba» (см. документ «Защищенная система управления базами данных «Jatoba». Руководство по установке).

Установка компонента «SQL_Firewall» в ОС GNU/Linux​

Установка компонента осуществляется в процессе установки СУБД «Jatoba», также компонент можно установить опционально после основной инсталляции СУБД.

Установку компонента возможно провести двумя способами:

  1. установка из локального репозитория (CDROM) – производится из файлов, записанных на компакт-диск или скопированных с него;

  2. установка непосредственно из deb/rpm-файлов – производится опционально, по усмотрению пользователя.

Компонент выполнен в виде отдельного deb или rpm-пакета. Установка компонента осуществляется средствами пакетного менеджера ОС. Для разных типов пакетных менеджеров команда установки немного отличается. Ниже приведены основные типы:

  • для систем на основе пакетного менеджера APT (к таким системам относятся все ОС семейства Debian, использующие deb-пакеты) команда установки следующая:
apt-get install jatoba<ver>-sql-firewall

Здесь и далее - номер используемой версии СУБД «Jatoba».

  • для систем на основе пакетных менеджеров YUM/DNF (к таким системам относятся все ОС семейства RedHat и вышедшие из нее, использующие rpm-пакеты) команда установки следующая:
yum install jatoba<ver>-sql-firewall

Отдельного уточнения требуют операционные системы ALT Linux.

  • ALT Linux использует пакетный менеджер APT, но распространяется в виде rpm-пакетов и для нее команда установки выглядит аналогично Debian:
apt-get install jatoba<ver>-sql-firewall

Установка компонента в составе других версий СУБД «Jatoba» осуществляется аналогично. Отличие будет только в номере версии СУБД, в составе которой он распространяется. Например, jatoba5-sql-firewall и т.п.

Удаление модуля также осуществляется средствами пакетного менеджера ОС. Вместо команды install нужно использовать соответствующую данному пакетному менеджеру команду удаления (remove, purge, erase и т.п.).

Для получения детальной информации по пакетному менеджеру рекомендуется обратиться к документации по ОС.

Настройка конфигурационного фала postgresql.conf​

В разделе «Shared Library Preloading», для последующей загрузки расширения, установить параметр:

shared_preload_libraries = 'sql_firewall'

Рисунок 2.1 – Параметр загрузки расширения

Дополнительная информация

В случае, если в параметре shared_preload_libraries также используется значение pg_stat_statements, то значение sql_firewall должно быть в обязательном порядке через запятую установлено после него:

shared_preload_libraries = 'pg_stat_statements, sql_firewall'

Для применения параметров потребуется перезапустить СУБД.

Установка расширения компонента «SQL_Firewall»​

После перезагрузки СУБД и загрузки расширения станет доступной установка расширения «sql_firewall».

Расширение устанавливается на всех узлах кластера при помощи SQL-команды:

CREATE EXTENSION sql_firewall;

В результате выполнения SQL-команды будет создано расширение (extension) «sql_firewall» в схеме данных.

ФУНКЦИОНАЛЬНЫЕ ВОЗМОЖНОСТИ​

Компонент «SQL_Firewall» выполнен в форме расширения СУБД и предназначен для фильтрации SQL-запросов (далее – «запрос»), поступающих в СУБД.

Фильтрация выполняется в два этапа:

  1. определение наличия SQL-инъекции в запросе. В случае наличия выполняется блокировка поступившего запроса в соответствии с указанными параметрами. Определение наличия SQL-инъекции выполняется с помощью обученной ML-модели (см. п. 3.2).

  2. определяется наличие запроса в перечне разрешенных для выполнения запросов (так называемые «белые» списки).

Режимы фильтрации SQL-запросов​

Компонент «SQL_Firewall» функционирует в следующих режимах, указанных в параметре sql_firewall.firewall:

  • "learning" – режим обучения;

  • "enforcing" – режим применения;

  • "permissive" – режим разрешающий любые SQL запросы;

  • "disabled" – режим отключенного модуля.

Дополнительная информация

Перед установкой параметра режима компонента «sql_firewall.firewall» в режимах «enforcing» или «permissive» необходимо активировать мониторинг всех метрик СУБД в режиме «learning» для того, чтобы используемые запросы вошли в состав разрешённых.

Режим обучения «learning»​

В режиме обучения модуль собирает информацию о пользователе и его запросах. Собирает, записывает и связывает информацию об идентификаторе пользователя «userid» и идентификаторе SQL-запроса «query id».

Значение «query id» устанавливается по дереву синтаксического анализа, аналогично расширению «pg_stat_statements».

Режим обучения инициализируется установкой параметра:

sql_firewall.firewall = 'learning'

в конфигурационном файле СУБД postgresql.conf и последующей перезагрузкой СУБД.

Рисунок 3.1 – Инициализация режима обучения

По умолчанию в режиме обучения может обработаться 5000 запросов. Запросы превышающие данное значение не будут изучаться.

Параметр изучаемых запросов может быть установлен от 100 до 5000, который устанавливается в конфигурационном файле СУБД postgresql.conf

Рисунок 3.2 – Установка параметра количества обрабатываемых SQL - запросов

Режим применения «enforcing»​

В режиме применения «enforcing», модуль проверяет находятся ли идентификатор пользователя «userid» и его SQL-запрос «query id» в паре, которая была ранее записана в режиме обучения «learning».

Если обнаруживается несоответствие, то пользователю выдается предупреждение о предотвращении выполнения.

Режим применения инициализируется установкой параметра:

sql_firewall.firewall = 'enforcing'

в конфигурационном файле СУБД postgresql.conf и последующей перезагрузкой СУБД.

Рисунок 3.3 – Инициализация режима применения

Режим разрешающий «permissive»​

В разрешающем режиме «permissive» модуль проверяет все запросы, но позволяет их выполнение, даже в случае, если таких запросов нет в правилах модуля. При несовпадениях выполняет запрос и сигнализирует пользователю о выявленном несоответствии.

Режим разрешения инициализируется установкой параметра:

sql_firewall.firewall = 'permissive'

в конфигурационном файле СУБД postgresql.conf и последующей перезагрузкой СУБД.

Рисунок 3.4 – Инициализация разрешающего режима

Режим отключения «disabled»​

В данном режиме компонент «SQL_Firewall» отключен и не проводит никаких действий. Данны режим включен по умолчанию.

Режим отключения компонента «SQL_Firewall» инициализируется установкой параметра:

sql_firewall.firewall = 'disabled'

в конфигурационном файле СУБД postgresql.conf и последующей перезагрузкой СУБД.

Рисунок 3.5 – Инициализация отключения модуля

Просмотр текущего режима фильтрации SQL-запросов​

Текущий режим фильтрации SQL-запросов возможно просмотреть при помощи SQL-команды:

SHOW sql_firewall.firewall;

Изменение режима фильтрации SQL-запросов​

В промышленной эксплуатации изменение режима фильтрации SQL-запросов без перезагрузки СУБД требуется для предотвращения прерывания сервиса у пользователей и снижения защитной функции компонента «SQL_Firewall».

Изменение режима фильтрации SQL-запросов выполняется при помощи SQL-команды следующего синтаксиса:

ALTER SYSTEM SET sql_firewall.firewall to '[mode_name]';

Где [mode_name] – название режима фильтрации SQL-запросов (см. п. 3.1) .

Пример:

ALTER SYSTEM SET sql_firewall.firewall to 'learning';

Далее необходимо перечитать текущую конфигурацию СУБД при помощи SQL-команды:

SELECT pg_reload_conf();

После этого можно проверить текущий режим фильтрации SQL-запросов (см. п. 3.1.5)

Режим обнаружения SQL-инъекций​

В данном режиме компонент «SQL_Firewall реализует функционал обнаружения SQL-инъекций в входящих запросах к СУБД.

Режим обнаружения SQL-инъекций доступен для компонента «SQL_Firewall» версии 1.1 с использованием СУБД «Jatoba» версии 5/6/18 при использовании ОС GNU/Linux. Список поддерживаемых ОС GNU/Linux приведен в документе «Руководство по установке» 643.72410666.00067-08 97 01

SQL-инъекция – это уязвимость, которая позволяет атакующей стороне использовать фрагмент вредоносного кода на языке SQL для получения доступа к потенциально ценной (коммерческой, конфиденциальной, персональной) информации и манипулирования СУБД.

Обнаружение SQL-инъекций производится с помощью обученной ML-модели (Machine Learning, машинное обучение), принцип которой приводится в п. 3.2.1.

Принцип работы ML-модели в компоненте SQL Firewall​

Модель машинного обучения обучена распознавать широкий спектр техник SQL-инъекций, включая, но не ограничиваясь: IN-BAND (включая ERROR-BASED и UNION-BASED), BLIND (включая TIME-BASED) и OUT OF BAND атаки.

Определяемые типы SQL-инъекций​

ML-модель компонента SQL Firewall детектирует следующие основные типы SQL-инъекций:

  1. IN-BAND SQLi – для атаки и получения данных используется один канал. К этому типу относятся:

    • ERROR-BASED (на основе ошибок) – вид атаки, при проведении которой нарушители используют сообщения об ошибках сервера базы данных для разведки и определения её структуры. В результате атаки будет передана ошибка, в тексте которой будет присутствовать полная версия используемой СУБД;
    AND (SELECT version())::int=1 -- -
    • UNION-BASED – предоставляет возможность получения информации с помощью оператора UNION для объединения результатов двух или более запросов SELECT. В ходе проведения атаки позволяет определить количество столбцов в исходном запросе. При совпадении количества NULL с количеством столбцов запрос выполнится, иначе возникнет ошибка.
    UNION ALL SELECT NULL, NULL, NULL; -- -

  2. BLIND SQLi («слепая» SQL-инъекция) – вид атаки, при которой ответ от базы данных можно получить лишь в формате «да»/«нет» (true/false) или через анализ времени ответа. Применение такой инъекции позволяет атакующему определить тип используемой базы данных: если это СУБД «Jatoba», то значение выражения будет True, иначе False.

AND substr(version(),1,10) = 'PostgreSQL' and '1'
  1. TIME-BASED (на основе времени ответа) – еще один тип «слепой» SQL-инъекций, при которой атакующий специально заставляют СУБД задержать ответ на запрос на несколько секунд. Таким образом злоумышленник может понять корректность составленного запроса.
SELECT CASE WHEN substring(datname,1,1)='1' THEN pg_sleep(5) ELSE pg_sleep(0) END FROM pg_database LIMIT 1;
  1. OUT OF BAND – атакующий отправляет SQL-запросы к СУБД способом, отличным от обычного взаимодействия. В качестве примера – использование DNS- или HTTP-запросов.

Определение вероятности SQL-инъекции​

Входящий запрос перед исполнением подается на обработку в ML-модель, которая возвращает в результате одно значение – вероятность (P) содержания во входящем запросе SQL-инъекции.

После этого значение P сравнивается с пороговым значением T, которое устанавливает администратором (см. далее п. 3.2.2).

При P ≤ T запросы считаются безопасными и допускаются к выполнению.

При P > T запрос классифицируется как содержащий SQL-инъекцию, и его выполнение прерывается с ошибкой.

Параметры режима обнаружения SQL-инъекций​

Параметры режима обнаружения SQL-инъекций определяются в конфигурационном файле postgresql.conf.

  1. sql_firewall.ml_enabled

Параметр отвечает за работу алгоритма определения SQL-инъекций.

Важная информация

При включённом режиме обнаружения в SQL-инъекций (sql_firewall.ml_enabled = 'true') запросы, исполняемые суперпользователями (например, postgres), не проверяются на наличие SQL-инъекций!

Тип: boolean

При значении «true» режим обнаружения SQL-инъекций включён, при «false» - выключен.

Значение по умолчанию: false

  1. sql_firewall.ml_score_threshold

Параметр определяет предельный порог T, при превышении которого обработанный запрос с значением P будет классифицироваться как содержащий SQL-инъекцию.

Тип: float

Значение по умолчанию: 0.35.

Дополнительная информация

В ходе тестирования ML-модели для компонента «SQL_Firewall» на синтетических данных установлено, что вариант с предобработкой демонстрирует более высокие значения метрик качества при снижении порогового значения ml_score_threshold ниже 0.5. Оптимальные результаты в рамках проведенных испытаний достигаются в диапазоне значений 0.3–0.35.

Следует учитывать, что значение параметра ml_score_threshold является подбираемым и зависит от особенностей конкретного экземпляра СУБД. Администратору рекомендуется самостоятельно определить оптимальное значение ml_score_threshold для своего экземпляра.

Пример.

Установлено стандартное значение порога ml_score_threshold = 0.35

В СУБД поступают два запроса, их вычисленное значение P — 0.25 и 0.75 соответственно.

В этом случае, первый запрос будет считаться безопасным, а второй – SQL-инъекцией, и он будет заблокирован компонентом.

Механизм исключений для групп ролей пользователей​

Механизм исключений предназначен для гибкого управления политикой правил

«белых» списков SQL-запросов. Он позволяет выборочно отключать блокировку неавторизованных SQL-запросов для определённых групп ролей пользователей, сохраняя при этом регистрацию всех неразрешённых действий в функциональном журнале событий компонента. Данный механизм может потребоваться для работы других компонентов, расширений или служб, которые взаимодействуют с СУБД «Jatoba» от имени не привилегированного пользователя, например «jaDog», «pg_profile», «ja_Log» и так далее.

В компоненте «SQL_Firewall» применяется служебная роль sql_firewall_privileged, которая не может быть использована для входа и установки сессии. Данная служебная роль предназначена исключительно для назначения прав доступа (GRANT) другим ролям (пользователям) с целью включения их в список исключений.

Рисунок 3.10 – Cлужебная роль sql_firewall_privileged

Служебная роль sql_firewall_privileged создается автоматически при установке расширения sql_firewall (см. п. 2.3).

Дополнительная информация

Суперпользователи (роли с атрибутом SUPERUSER) не требуют явного назначения служебной роли sql_firewall_privileged. Для них исключение из проверки «белых» списков действует автоматически.

Запросы суперпользователей, отсутствующие в «белом» списке, также подлежат обязательному логированию (при уровне info) аналогично обычным ролям-исключениям.

Правила обработки SQL-запросов для ролей-исключений:

  1. Для всех пользователей, которым явно выданы права служебной роли sql_firewall_privileged, например с помощью команды,
GRANT sql_firewall_privileged TO имя_пользователя;

механизм блокировки SQL-запросов на основе «белых» списков не применяется, даже если его шаблон отсутствует в «белом» списке (sql_firewall_statements).

  1. При уровне журналирования info каждый неавторизованный запрос (отсутствующий в «белом» списке) фиксируется в журнале СУБД с указанием:

    • имени роли пользователя;

    • содержимого SQL-запроса;

    • дате и времени выполнения.

Ограничения применения механизма исключений для ролей пользователей:

  • аутентификация и установка сессии от имени служебной роли sql_firewall_privileged запрещены на уровне СУБД. Попытка подключения с использованием роли sql_firewall_privileged отклоняется;

  • служебная роль sql_firewall_privileged не наследуется автоматически; необходимо явное назначение для каждой целевой роли;

  • для корректной работы административных и служебных учётных записей, где применение строгой политики «белых» списков нежелательно, рекомендуется включать их в список исключений через назначение служебной роли sql_firewall_privileged (либо использовать атрибут SUPERUSER).

Добавление групповых ролей в список исключений​

Порядок настройки исключений для ролей пользователей:

  1. Просмотр текущих правил брандмауэра выполняется SQL-командой:
SELECT * from sql_firewall.sql_firewall_statements;
  1. Выдать права доступа служебной роли sql_firewall_privileged требуемому пользователю или группе ролей при помощи следующего SQL-запроса:
GRANT sql_firewall_privileged TO user_priveleged;
  1. Выдать права на схему данных public нужному пользователю при помощи следующего SQL-запроса:
GRANT ALL PRIVILEGES ON SCHEMA public TO user_priveleged;

Рисунок 3.11 – Создание пользователя и выдача необходимых прав доступа

  1. Проверить наследование прав доступа для пользователя при помощи следующего SQL-запроса:
WITH RECURSIVE role_hierarchy AS ( 
    
    SELECT oid, rolname

    FROM pg_roles

    WHERE rolname = 'sql_firewall_privileged' 

UNION ALL

SELECT r.oid, r.rolname

FROM pg_catalog.pg_roles r

JOIN pg_catalog.pg_auth_members m ON (m.member = r.oid) JOIN role_hierarchy rh ON (m.roleid = rh.oid)

)

SELECT rolname AS username FROM role_hierarchy r

WHERE r.rolname <> 'sql_firewall_privileged'

    AND EXISTS (SELECT 1 FROM pg_roles WHERE oid = r.oid AND rolcanlogin)

ORDER BY 1;

Рисунок 3.12 – Проверка наследования прав доступа sql_firewall_privileged

Отсутствие в полученном результате названия пользователя или групповой роли говорит о том, что к ним не будет применяться исключение при выполнении SQL-запросов в СУБД.

  1. Установить режим применения «enforcing» (см. п. 3.1.2) или разрешающий (см. п. 3.1.3) режимы работы компонента «SQL_Firewall», а также необходимый уровень журналирования событий в конфигурационном файле postgresql.conf:
sql_firewall.firewall = 'enforcing' 
log_min_messages = info

  1. Перезагрузить СУБД для применения настроек.

  2. Авторизоваться в СУБД и выполнить несколько запросов, не входящих в «белый список», от имени пользователя, для которого включен механизм исключений.

Рисунок 3.13 – Проверка выполнения запросов от имени пользователя, для которого включен механизм исключений

  1. По успешности выполнения SQL-запросов убедится в том, что к пользователю, для которого включен механизм исключений, не применяются правила брандмауэра.

  2. Авторизоваться в СУБД от имени привилегированного пользователя и проверить содержимое правил компонента «SQL_Firewall» при помощи следующего SQL-запроса:

SELECT s.userid, u.rolname AS username, s.queryid, s.query, s.calls
    FROM sql_firewall.sql_firewall_statements s JOIN
    pg_authid u ON s.userid = u.oid WHERE u.rolname = 'user_priveleged';

В таблице не должны быть отражены SQL-запросы пользователя, для которого был включен механизм исключений.

Отключение механизма исключений для групп ролей пользователей состоит в отзыве служебной роли sql_firewall_privileged для пользователя и выполняется при помощи следующего SQL-запроса:

REVOKE sql_firewall_privileged FROM имя_пользователя;

Управление обучением белого списка для привилегированных пользователей​

В состав компонента «SQL Firewall» включён параметр конфигурации learn_privileged_user_queries, управляющий регистрацией SQL-запросов от привилегированных пользователей в «белом» списке (sql_firewall_statements) в режиме обучения «learning» (см. п. 3.1.1).

Дополнительная информация

Параметр learn_privileged_user_queries действует исключительно в режиме «learning». В режимах «permissive» и «enforcing» его значение не влияет на фильтрацию или блокировку SQL-запросов

Функциональность ролей-исключений (см. п. 3.3.1) сохраняется в полном объёме – для привилегированных пользователей блокировка не применяется независимо от значения параметра learn_privileged_user_queries.

Определение привилегированных пользователей:

  • пользователи, имеющие атрибут SUPERUSER;

  • пользователи, которым явно назначена роль sql_firewall_privileged (см. п. 3.3.1). Значения параметра learn_privileged_user_queries:

  • on (значение по умолчанию) – в режиме обучения (sql_firewall.firewall = 'learning') все запросы от привилегированных пользователей добавляются в «белый» список наравне с запросами обычных пользователей;

  • off – в режиме обучения «learning» запросы привилегированных пользователей не добавляются в «белый» список. Обучение ведётся только на основе запросов обычных пользователей (не имеющих суперпривилегий и не входящих в группу sql_firewall_privileged).

Отключение параметра learn_privileged_user_queries производится при помощи следующих команд:

ALTER SYSTEM SET learn_privileged_user_queries = off; 
SELECT pg_reload_conf();
Дополнительная информация

Параметр learn_privileged_user_queries имеет значение по умолчанию – активирован.

Текущее значение параметра learn_privileged_user_queries можно узнать выполнив следующий запрос:

SHOW sql_firewall.learn_privileged_user_queries;

В результате будет возвращено значение:

sql_firewall.learn_privileged_user_queries​

on

Переносимость «белых списков» между версиями и экземплярами СУБД​

Механизм переноса «белых списков» (White List) правил компонента «SQL_Firewall» позволяет сохранить накопленные правила при обновлении, миграции или переносе СУБД «Jatoba» на другой экземпляр. Это сокращает время на повторное обучение и обеспечивает непрерывность защиты.

Дополнительная информация

Функции экспорта/импорта доступны только в режиме disabled (SQL_Firewall отключён) и требуют прав суперпользователя (Superuser).

Все описанные далее способы полностью совместимы с режимами работы модуля learning, permissive и enforcing.

Переносимость «белых списков» гарантируется для следующих сценариев:

  • обновление в рамках одной мажорной версии СУБД (минорные обновления пакетов);

  • перенос между экземплярами одной мажорной версии СУБД;

  • мажорное обновление СУБД с помощью утилиты pg_upgrade (правила сохраняются автоматически);

  • миграция между разными мажорными версиями СУБД через экспорт/импорт правил компонента SQL_Firewall;

  • перенос «белых списков» только с младшей версии компонента «SQL_Firewall» к старшей, например, с версии 1.0 до версии 1.2.

Ограничения:​

  • при обновлении на другую мажорную версию СУБД (например, с 16.1 на 18.1) без использования pg_upgrade расчёт query_id может измениться, поэтому перенос «белых списков» не гарантируется. Исключение составляют сборки, начиная с версии 1.1.0-68, в которых поддержка переноса между мажорными версиями СУБД реализована полностью;

  • в пределах одной мажорной версии СУБД (4, 5, 6, 18 и т.д.) вычисление значения query_hash идентично на любых экземплярах.

Способы переноса «белых списков» представлены в таблице 4.1.

Перенос «белых списков» после мажорного обновления СУБД (pg_upgrade)​

Выполняется в следующей последовательности:

  1. Выполнить обновление пакетов ядра СУБД и компонента SQL_Firewall согласно процедурам из документа «Руководство по обновлению» 643.72410666.00067-08 93 01.

  2. Подключиться к СУБД и обновить расширение компонента SQL_Firewall:

ALTER EXTENSION sql_firewall UPDATE;

Если версия расширения в новой мажорной версии СУБД изменилась: расширение будет обновлено. Если версия расширения в новой мажорной версии СУБД не изменилась будет выведено сообщение о том, что версия расширения sql_firewall уже установлена.

  1. Убедится в том, что версия расширения компонента соответствует устанавливаемой:
\dx
  1. Проверить таблицу с «белым списком» компонента:
SELECT * FROM sql_firewall.sql_firewall_statements;

Таблица содержит записи, которые были внесены на предыдущей версии СУБД.

  1. Открыть конфигурационный файл postgresql.conf и установить значение параметра:
sql_firewall.firewall = 'permissive'

После внесения изменений выполнить перезагрузку служб СУБД.

  1. Подключиться к СУБД и выполнить содержимое «белого списка»:
SELECT * FROM sql_firewall.sql_firewall_statements;

Таблица содержит список запросов.

  1. Выполнить запросы из «белого списка». Запросы должны быть успешно выполнены.

  2. Выполнить несколько запросов, которых нет в таблице правил. Запросы должны быть выполнены, но с предупреждением (т.к. отсутствуют в таблице правил).

  3. Открыть конфигурационный файл postgresql.conf и установить значение параметра:

sql_firewall.firewall = 'enforcing'

После внесения изменений выполнить перезагрузку служб СУБД.

  1. Выполнить несколько запросов, которых нет в таблице правил. Запросы не выполнены, сообщение об ошибке: ERROR: Prohibited SQL statement.

После этого перенос «белых списков» считается выполненным успешно.

Перенос «белых списков» между экземплярами разных мажорных версий СУБД​

Выполняется в следующей последовательности:

  1. Остановить службу СУБД и создать еще один новый экземпляр:
# systemctl stop jatoba-* 
# su – postgres
/usr/jatoba-*/bin/initdb -D /var/lib/jatoba/<ver>/data-new -c port=5433

  1. Выполнить установку компонента согласно разделу 2.

  2. Подключиться к первому экземпляру и экспортировать правила согласно п. 4.2.1.

  3. Открыть конфигурационный файл postgresql.conf нового экземпляра СУБД и установить значение параметра:

sql_firewall.firewall = 'disabled'

После внесения изменений перезапустить службу СУБД.

  1. Подключиться к новому экземпляру СУБД и импортировать правила согласно п. 4.2.2.

  2. Проверить наличие импортированных правил в новом экземпляре:

SELECT * FROM sql_firewall.sql_firewall_statements;
  1. Открыть конфигурационный файл postgresql.conf нового экземпляра СУБД и установить значение параметра:
sql_firewall.firewall = 'permissive'

После внесения изменений перезапустить службу нового экземпляра СУБД.

  1. Подключиться к новому экземпляру СУБД и выполнить запросы из «белого списка». Запросы должны быть успешно выполнены.

  2. Выполнить несколько запросов, которых нет в таблице правил. Запросы должны быть выполнены, но с предупреждением (т.к. отсутствуют в таблице правил).

  3. Открыть конфигурационный файл postgresql.conf и установить значение параметра:

sql_firewall.firewall = 'enforcing'

После внесения изменений перезапустить службу нового экземпляра СУБД.

  1. Выполнить несколько запросов, которых нет в таблице правил. Запросы не выполнены, сообщение об ошибке: ERROR: Prohibited SQL statement.

После этого перенос «белых списков» считается выполненным успешно.

Перенос «белых списков» между экземплярами одной версии СУБД (экспорт и импорт) с созданием новой директории для СУБД​

Выполняется в следующей последовательности:

  1. Остановить службу СУБД и создать еще один экземпляр:
# systemctl stop jatoba-* 
# su – postgres
/usr/jatoba-*/bin/initdb -D /var/lib/jatoba/<ver>/data-new -c port=5433
  1. Открыть конфигурационный файл postgresql.conf и установить значение параметра:
shared_preload_libraries = 'sql_firewall' 
sql_firewall.firewall = 'disabled'
  1. Запустить новый экземпляр СУБД от имени системного пользователя postgres:
/usr/jatoba-*/bin/pg_ctl -D /var/lib/jatoba/<ver>/data-new start
  1. Подключиться к новому экземпляру СУБД и установить расширение компонента SQL_Firewall:
CREATE EXTENSION sql_firewall;
  1. Проверить таблицу с «белым списком» компонента:
SELECT * FROM sql_firewall.sql_firewall_statements;

Таблица не должна содержать записей.

  1. Импортировать правила согласно п. 4.2.2.

  2. Вывести содержимое таблицы с «белым списком» как это указано в пп. 5): Импортированные правила присутствуют в таблице sql_firewall_statements.

  3. Открыть конфигурационный файл postgresql.conf и установить значение параметра:

sql_firewall.firewall = 'permissive'

Перезапустить новый экземпляр СУБД от имени системного пользователя postgres:

/usr/jatoba-*/bin/pg_ctl -D /var/lib/jatoba/<ver>/data-new restart

  1. Подключиться к СУБД и выполнить запросы из «белого списка». Запросы должны быть успешно выполнены.

  2. Выполнить несколько запросов, которых нет в таблице правил. Запросы должны быть выполнены, но с предупреждением (т.к. отсутствуют в таблице правил).

  3. Открыть конфигурационный файл postgresql.conf и установить значение параметра:

sql_firewall.firewall = 'enforcing'

Перезапустить новый экземпляр СУБД от имени системного пользователя postgres:

/usr/jatoba-*/bin/pg_ctl -D /var/lib/jatoba/<ver>/data-new restart

  1. Подключиться к СУБД и выполнить запросы из «белого списка». Запросы должны быть успешно выполнены.

  2. Выполнить несколько запросов, которых нет в таблице правил. Если запросы не были выполнены, то будет выведено сообщение об ошибке:

ERROR: Prohibited SQL statement

После этого перенос «белых списков» считается выполненным успешно.

Перенос «белых списков» при минорном обновлении пакетов (в рамках одной мажорной ветки СУБД)​

Выполняется в следующей последовательности:

  1. Выполнить обновление пакетов ядра СУБД и компонента SQL_Firewall согласно процедурам из документа «Руководство по обновлению» 643.72410666.00067-08 93 01.

  2. После запуска сервисов СУБД обновить расширение:

ALTER EXTENSION sql_firewall UPDATE;
  1. Открыть конфигурационный файл postgresql.conf и установить значение параметра:
sql_firewall.firewall = 'permissive'

После чего перезапустить сервисы СУБД.

  1. Вывести содержимое таблицы с «белым списком»:
SELECT * FROM sql_firewall.sql_firewall_statements;

Список должен содержать запросы с значением queryid до обновления.

  1. Открыть конфигурационный файл postgresql.conf и установить значение параметра:
sql_firewall.firewall = 'enforcing'
  1. Выполнить запросы, не содержащиеся в «белом списке» и убедится в том, что они прерываются с ошибкой.

После этого перенос «белых списков» считается выполненным успешно.

Проверка правил после импорта​

После импорта правил рекомендуется выполнить проверку:

SELECT * FROM sql_firewall.sql_firewall_statements;

Данный запрос должен отобразить все правила, загруженные после импорта. Для проверки счётчиков предупреждений и ошибок используется другой запрос:

SELECT * FROM sql_firewall.sql_firewall_stat;

ВЗАИМОДЕЙСТВИЕ С ДРУГИМИ КОМПОНЕНТАМИ​

Взаимодействие с компонентом «jaDog»​

В рассматриваемом примере взаимодействия с компонентом «jaDog» используется механизм синхронизации файлов с правилами компонента «SQL_Firewall» между главным узлом и резервными. Механизм синхронизации файлов встроен в компонент «jaDog» и не требует установки дополнительного программного обеспечения.

Предварительными условиями на всех узлах создаваемого кластера:

  • расширение sql_firewall установлено (см. п. 2.3);

  • компонент «SQL_Firewall» работает в режиме обучения «learning» (см. п. 3.1.1). В процессе создания кластера SQL-запросы будут записаны в список правил (см. п. 4.1.1);

Создание и настройка отказоустойчивого кластера на основе компонента «jaDog» приводятся в документе «Руководство по настройке. Часть 1. Управление режимом работы узлов кластера. Компонент «jaDog» 643.72410666.00067-08 98 02-01.

Последующая настройка взаимодействия компонентов между собой на главном узле выполняется в следующем порядке:

  1. Подключиться к консольной утилите jadog_ctl и перевести кластер в режим технического обслуживания.

  2. Перевести компонент «SQL_Firewall» в режим отключения «disabled» (см. п. 3.1.4).

  3. Перезагрузить службу СУБД. В этот момент будут записаны SQL-запросы в файл PGDATA/pg_stat/sql_firewall_statements.stat.

  4. Экспортировать список правил в текстовый файл:

SELECT sql_firewall_export_rule('/var/lib/jatoba/18/rule.txt');
  1. Подключиться к консольной утилите jadog_ctl и выполнить следующие команды:
fm set '/var/lib/jatoba/18/rule.txt' fm copy

После этого текстовый файл с правилами будет реплицирован с главного узла на все резервные. Следующие шаги выполняются на резервных узлах.

  1. Для импорта правил необходимо перевести компонент «SQL_Firewall» в режим отключения «disabled» (см. п. 3.1.4).

  2. Перезагрузить службу СУБД.

  3. Для импорта правил из текстового файла необходимо выполнить команду:

SELECT sql_firewall_import_rule('/var/lib/jatoba/18/rule.txt');

  1. После завершения импорта необходимо установить требуемый режим работы компонента «SQL_Firewall» (см. п. 3.1).

  2. На главном узле подключиться к консольной утилите jadog_ctl и вывести кластер из режима технического обслуживания.

Взаимодействие с компонентом «ja_Hipe_Cluster»​

В данном подразделе рассматривается взаимодействие с компонентом «ja_Hipe_Cluster».

В рамках описываемого сценария компонент «SQL_Firewall» уже установлен на будущих узлах кластера, а компонент «ja_Hipe_Cluster» устанавливается и настраивается в дальнейшем.

Информация об установке компонента «ja_Hipe_Cluster» и настройке кластера приводится в документе «Руководство по настройке. Часть 11. Высокопроизводительный кластер. Компонент «ja_Hipe_Cluster» 643.72410666.00067-08 98 01-11.

Последующая настройка взаимодействия компонентов между собой выполняется на всех узлах кластера в следующем порядке:

  1. На будущих узлах установить пакеты компонента «ja_Hipe_Cluster»

  2. В конфигурационном файле postgresql.conf для параметра разделяемых библиотек shared_preload_libraries первым указывать значение «citus»:

shared_preload_libraries = 'citus, sql_firewall'

  1. Перевести компонент «SQL_Firewall» в режим отключения (см. п. 3.1.4) и очистить правила (см. п. 4.2.3);

  2. Перезагрузить службу СУБД;

  3. Установить на все узлы кластера расширение «citus» согласно документации на компонент.

  4. После завершения распределения таблиц в высокопроизводительном кластере с узла-координатора выполнить включение режима обучения (см. п. 3.1.1) на всех рабочих узлах кластера при помощи следующих команд:

SELECT run_command_on_all_nodes($$ALTER SYSTEM SET sql_firewall.firewall = 'learning';$$);
SELECT run_command_on_all_nodes($$SELECT pg_reload_conf();$$);

  1. На узле-координаторе необходимо выполнить те SQL-запросы, которые должны быть записаны в список правил в качестве разрешаемых.

  2. После завершения наполнения списка правил с узла-координатора на всех узлах кластера установить требуемый режим работы компонента «SQL_Firewall» (permissive или enforcing):

SELECT run_command_on_all_nodes($$ALTER SYSTEM SET sql_firewall.firewall = '**permissive**';$$);

Или

SELECT run_command_on_all_nodes($$ALTER SYSTEM SET sql_firewall.firewall = '**enforcing**';$$);
  1. С узла-координатора на всех узлах кластера выполнить чтение конфигурационного файла postgresql.conf:
SELECT run_command_on_all_nodes($$SELECT pg_reload_conf();$$);
Дополнительная информация

Списки правил на рабочих узлах будут сформированы компонентом «SQL_Firewall» отдельно для каждого из них.

  1. Режим обнаружения SQL-инъекций (см. п. 3.2) необходимо включать только на узле-координаторе, а на рабочих узлах этот параметр должен иметь значение «false».

ОБНОВЛЕНИЕ​

Обновление компонента выполняется согласно документу «Руководство по обновлению» 643.72410666.00067-08 93 01.

УДАЛЕНИЕ​

Для полного удаления компонента «SQL_Firewall» необходимо выполнить следующие действия:

  1. перевести компонент «SQL_Firewall» в режим отключения «disabled» в конфигурационном файле postgresql.conf:
#sql_firewall.firewall = 'disabled'

и перезапустить службу СУБД.

  1. Очистить списки правил и статистики:
SELECT sql_firewall_reset(); 
SELECT sql_firewall_stat_reset();
  1. удалить расширение компонента «SQL_Firewall» SQL-командой:
DROP EXTENSION sql_firewall;
  1. удалить или закомментировать в конфигурационном файле postgresql.conf загрузку компонента:
#shared_preload_libraries = 'sql_firewall' 
#sql_firewall.max = 5000
  1. перезапустить службу СУБД.
