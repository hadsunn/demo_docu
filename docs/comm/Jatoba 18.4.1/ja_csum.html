Компонент «ja_CSum». Контроль целостности.

АННОТАЦИЯ

В документе приведены сведения, необходимые для установки и эксплуатации компонента «ja_CSum» (далее по тексту – «компонент» или ja_CSum), предназначенного для выполнения периодических фоновых проверок файлов.

Настоящее руководство предназначено для администраторов СУБД.

Дополнительная информация

Все примеры в данном документе приведены для СУБД «Jatoba» версии ядра 4.x, для других версий все шаги выполняются аналогично, разница состоит в именах директорий.

Например, СУБД «Jatoba» версии 6.x по умолчанию устанавливается в директорию ОС Linux – «/usr/jatoba-6/bin».

Для СУБД «Jatoba» версии ядра 4 используется версия компонента — 1.0.

Для СУБД «Jatoba» версии ядра 5/6/18 используется версия компонента — 2.1.

НАЗНАЧЕНИЕ КОМПОНЕНТА​

Компонент «ja_CSum» предназначен для выполнения периодических фоновых проверок целостности файлов СУБД «Jatoba».

Условия применения​

Компонент «ja_CSum» может использоваться с СУБД «Jatoba» версий 4.x и выше, под управлением операционной системы GNU/Linux.

Важная информация

В текущей реализации компонента не поддерживается управление через компонент пользовательского веб-интерфейса для администраторов «Jatoba data safe».

Ограничений по совместимости с другими компонентами нет.

УСТАНОВКА И НАСТРОЙКА​

Установка компонента «ja_CSum» должна производится от имени пользователя, обладающего административными привилегиями в операционной системе. Данный компонент штатным образом может быть установлен только с СУБД «Jatoba» (см. документ «Защищенная система управления базами данных «Jatoba». Руководство по установке).

Установка компонента «ja_CSum» в ОС GNU/Linux​

Компонент устанавливается в составе СУБД «Jatoba». Его возможно установить при первичной установке либо доустановить.

Установку компонента возможно провести двумя способами:

  1. установка из локального репозитория (CDROM) – производится из файлов, записанных на компакт-диск или скопированных с него;

  2. установка непосредственно из deb/rpm-файлов – производится опционально, по усмотрению пользователя.

Компонент выполнен в виде отдельного deb или rpm-пакета. Установка компонента осуществляется средствами пакетного менеджера ОС. Для разных типов пакетных менеджеров команда установки немного отличается. Ниже приведены основные типы:

  • для систем на основе пакетного менеджера APT (к таким системам относятся все ОС семейства Debian, использующие deb-пакеты) команда установки следующая:
# apt-get install jatoba<ver>-ja-csum
  • для систем на основе пакетных менеджеров YUM/DNF (к таким системам относятся все ОС семейства RedHat и вышедшие из нее, использующие rpm-пакеты) команда установки следующая:
# yum install jatoba<ver>-ja_csum
# dnf install jatoba<ver>-ja_csum

Отдельного уточнения требуют операционные системы ALT Linux и openSUSE.

  • ALT Linux использует пакетный менеджер APT, но распространяется в виде rpm-пакетов и для нее команда установки выглядит аналогично Debian:
# apt-get install jatoba<ver>-ja_csum

Установка компонента в составе других версий СУБД «Jatoba» осуществляется аналогично. Отличие будет только в номере версии СУБД, в составе которой он распространяется. Например, jatoba4-ja_csum и т.п.

Удаление модуля также осуществляется средствами пакетного менеджера ОС. Вместо команды install нужно использовать соответствующую данному пакетному менеджеру команду удаления (remove, purge, erase и т.п.).

Для получения детальной информации по пакетному менеджеру рекомендуется обратиться к документации по ОС.

Настройка конфигурационного файла «postgresql.conf»​

Для осуществления контроля целостности (расчета контрольных сумм, далее КС) программного обеспечения и выполнения меры защиты информации ОЦЛ.1 потребуется в конфигурационном файле «postgresql.conf» установить параметры регистрации событий в СУБД.

Файл расположен в каталоге:

/var/lib/jatoba/<ver>/data/

В нем в разделе «REPORTING AND LOGGING» рекомендуется проверить наличие активных параметров:

log_destination = 'csvlog' 
logging_collector = on 
log_directory = 'log'

Для передачи событий безопасности средствами компонента «ja_Log» в пользовательский веб-интерфейс для администраторов «Jatoba data safe», параметр «log_destination» рекомендуется установить на формирование файлов в формате *.csv.

Уровень детализации сообщений в параметре «log_min_messages» должен быть установлен не ниже параметра «warning», а рекомендованный параметр – «info»:

log_min_messages = info

shared_preload_libraries = 'ja_csum'

shared_preload_libraries = 'securityprofile, ja_csum'

Дополнительные настройки конфигурационного файла «postgresql.conf» и процесс установки для компонента «SecurityProfile» описаны в документе руководство администратора, в разделе 6 «Настройка безопасности СУБД «Jatoba».

Установка расширения «ja_csum»​

Установка расширения «ja_csum» выполняется автоматически при первом старте СУБД. Для чего достаточно:

  • в разделе «Shared Library Preloading» для последующей загрузки расширения установить параметр:
shared_preload_libraries = 'ja_csum'
  • в разделе «CUSTOMIZED OPTIONS» для установки расширения в БД установить параметр:
ja_csum.db_name = 'postgres'

Рисунок 2.4 – Параметр установки расширения «ja_csum» в БД

Дополнительная информация

Если параметр ja_csum.db_name явно не задан в конфигурационном файле postgresql.conf, то для установки расширения ja_csum по умолчанию будет использоваться БД «postgres». Установка расширения выполняется в том случае, если также определен параметр ja_csum.check_auto = on

В случае, если расширение ja_csum не было установлено в БД, заданную в параметре ja_csum.db_name, то в журнал работы СУБД записывается сообщение:

extension ja_csum is not installed

– в разделе «CUSTOMIZED OPTIONS» определить файловый каталог, в котором будет храниться файл контрольных сумм через параметр (определяется через параметр ja_csum.work_dir):

ja_csum.work_dir = '/var/lib/jatoba/18/data/ja_csum'
Дополнительная информация

Если параметр ja_csum.work_dir явно не задан, то при установке расширения ja_csum он будет создан внутри каталога PGDATA, например, /var/lib/jatoba//data/ja_csum ( - соответствует номеру установленной версии СУБД «Jatoba»).

Каталог с файлами контрольных сумм, указанный в параметре ja_csum.work_dir, должен находиться внутри каталога данных СУБД - PGDATA.

При ручном создании каталога с файлами контрольных сумм пользователь ОС postgres должен иметь на него права доступа «0700». В ином случае создание каталога прерывается, а в журнал работы СУБД записывается сообщение:

В случае, если каталог, указанный в параметре ja_csum.work_dir, не расположен внутри каталога PGDATA, то в журнал работы СУБД будет выведено сообщение:

can't create directory [ja_csum.work_dir_name] specified in parameter ja_csum.work_dir: [mkdir_error]

Где <work_dir> - название каталога, указанного в параметре ja_csum.work_dir конфигурационного файла postgresql.conf.

В случае, если каталог, заданный параметром ja_csum.work_dir не может быть создан, то в журнал работы СУБД будет выведено сообщение

can't create directory <work_dir> specified in parameter ja_csum.work_dir: ошибка

– в разделе «CUSTOMIZED OPTIONS» определить автоматическую установку расширения в БД (определяется через параметр ja_csum.db_name):

ja_csum.auto_create_extension = on
Дополнительная информация

В случае, если параметр ja_csum.auto_create_extension = on, то ручное выполнение команды «CREATE EXTENSION ja_csum» не требуется, что удобно для случаев автоматизированного развертывания компонента ja_CSum» например в отказоустойчивых кластерах компонента «jaDog».

Важная информация

В случае применения компонента «ja_CSum» совместно с компонентом высокопроизводительного кластера «ja_Hipe_Cluster» и отказоустойчивого кластера «jaDog» параметр должен быть ja_csum.auto_create_extension = off.

После определения всех необходимых параметров в конфигурационном файле postgresql.conf необходимо выполнить перезапуск СУБД при помощи команды:

# systemctl restart jatoba-<ver>

В результате при запуске СУБД будет создана схема данных «ja_csum», одноименное расширение и созданы файлы с контрольными суммами.

ФУНКЦИОНАЛЬНЫЕ ВОЗМОЖНОСТИ КОМПОНЕНТА​

Компонент «ja_CSum» служит для выполнения контроля целостности файлов СУБД и БД, а также для ограничения программной среды в СУБД.

Для выполнения блокировки пользователей СУБД и БД используется дополнительный компонент «SecurityProfile», входящий в состав СУБД «Jatoba». Обязательные контролируемые объекты БД:

  • процедуры и функции, написанные на языках C, SQL, plpgsql и других;

  • агрегатные функции;

  • триггеры на таблицы и представления;

  • триггеры на события;

  • представления;

  • материализованные представления;

  • пользовательские типы (композитные, перечисления, диапазоны). Обязательные контролируемые объекты СУБД:

  • «postgresql.conf» – главный конфигурационный файл СУБД;

  • «pg_hba.conf» – конфигурационный файл правил аутентификации в СУБД;

  • «pg_ident.conf» – конфигурационный файл сопоставлений имен пользователей для правил аутентификации в СУБД;

  • «postgresql.auto.conf» – конфигурационный файл, хранящий изменения, вносимые в конфигурацию СУБД через SQL-команду «ALTER SYSTEM».

В компоненте «ja_CSum» предопределены перечни, которые запрещены для изменения:

  • стандартных расширения PostgreSQL (см. Приложение 2);

  • компонентов, входящих в комплект поставки (см. Приложение 1).

Рекомендуется после загрузки расширений пересоздать файлы контрольных сумм, вызвав функцию SELECT ja_csum.fill_list(), как описано в п. 3.2 настоящего документа, т.к. в ходе установки расширения будут добавлены новые данные (таблицы, схемы, функции и т.д.). Новые объекты должны быть поставлены на контроль, чтобы исключить срабатывания механизма блокировки пользователей в СУБД.

Первый запуск компонента​

После загрузки СУБД, компонент выполнит расчет и последующую проверку КС, так как по умолчанию будет включен режим «auto».

В журнале сообщений появится сообщение:

ja_csum * check_sum_event * stop_object_check * auto

Если компонент не обнаружит установленного расширения, то запишет информационное сообщение описанное в п. 8.2

ja_csum * check_sum_event * extension securityprofile not found

Расчет КС файлов СУБД (ja_csum.fill_list)​

Список контролируемых файлов создается SQL-командой:

SELECT ja_csum.fill_list();

Рисунок 3.1 – Команда создания файла с контрольными суммами

В результате выполнения SQL-команды будет создан каталог по пути в:

/var/lib/jatoba/_номер_версии_/ja_csum

Требования к каталогу с файлами КС приведены в п. 2.3.

Ограничения на запуск функции ja_csum.fill_list() приведены в п. 3.13.

Структура служебного каталога и формат файлов эталонных КС​

В каталоге хранения файлов КС будет создан файл контроля с конфигурационными файлами СУБД.

Рисунок 3.2 – Каталог с файлом контрольных сумм

Файл контроля конфигурационных файлов СУБД имеет название следующего формата «fs_checksums__.csv» и формат полей:

– полный путь к файлу;

– имя файла;

– дата модификации файла (UTC+0) в формате "ДД.ММ.ГГ ЧЧ:ММ:CC";

– размер файла, в байтах;

– контрольная сумма файла (по алгоритму MD5).

Поля файла контроля конфигурационных файлов СУБД разделены запятыми.

Рисунок 3.3 – Пример содержимого файла контрольных сумм «fs_checksums_node54_5432.csv»

Файл контроля конфигурационных файлов СУБД содержит следующие записи:

– postgresql.auto.conf;

– postgresql.conf;

– pg_hba.conf;

– pg_ident.conf.

При первом расчете КС будет создан каталог backup_configfiles, который содержит резервные копии конфигурационных файлов СУБД (описание содержимого данного каталога приведено в п. 3.14.6)

В процессе первого расчета КС также дополнительно создается временный файл текущих КС конфигурационных файлов СУБД «fs_checksums___new.csv»

Также в каталоге в процессе расчета КС будут следующие временные файлы:

– контроля объектов СУБД db_.csv;

– контроля бинарных файлов binary__.csv.

После успешного завершения расчета КС данные временные файлы удаляются.

Установка периодичности проверки (ja_csum.check_interval)​

В соответствии с «Требованиями по безопасности информации к системам управления базами данных (выписка)», утвержденными Приказом ФСТЭК России № 64 от 14.04.2023, контроль целостности СУБД должен проводится не менее 1 раза в сутки. Для выполнения данного требования по умолчанию установлен параметр «1440» минут, что соответствует количеству минут в сутках.

Соответственно отсчет времени начнется с момента первой проверки.

Рисунок 3.5 – Проверка установленного интервала проверки

Периодичность проверки контрольных сумм устанавливается SQL-командой:

ALTER SYSTEM SET ja_csum.check_interval = <number of minutes>;

Параметр интервала проверок может быть установлен в диапазоне от 1 до 35 000 минут. Отрицательные и дробные значения не допускаются.

При установке параметра:

  • выполнится внеочередная проверка;

  • компонент запомнит время выполнения проверки;

  • время выполнения последующих проверок будет отсчитываться от времени выполнения SQL-команды, т.е. от времени установки параметра «ja_csum.check_interval».

Например

Для установки периодичности проверки КЦ раз в 2880 минут выполняется SQL-команда:

ALTER SYSTEM SET ja_csum.check_interval = 2880;

После чего выполняется проверка установленного параметра SQL-командой:

Режимы работы компонента (ja_sum.action_mode)​

Компонент работает в дух режимах:

  • «permissive» (режим информирования);

  • «enforcing» (режим блокирования).

Вывод текущего режима работы компонента выполняется SQL-командой:

SHOW ja_csum.action_mode;

При запуске компонента, по умолчанию устанавливается режим «блокирования».

Управление функцией «ja_sum.action_mode» возможно от имени и с правами привилегированного пользователя (администратора СУБД) с атрибутом «SUPERUSER».

Режим информирования «permissive»​

Режим информирования «permissive» может использоваться при вводе СУБД в эксплуатацию, когда окончательно не сформировался список используемых расширений и настроек СУБД.

Получаемые сообщения от компонента в журнале событий, позволят администратору СУБД проанализировать их, окончательно настроить СУБД и минимизировать риск нарушения контроля целостности с последующей блокировкой пользователей.

В данном режиме блокировка пользователей не осуществляется.

Установка режима информирования «permissive» выполняется SQL-командой:

ALTER SYSTEM SET ja_csum.action_mode = 'permissive';

SELECT pg_reload_conf();

Режим блокирования «enforcing»​

Режим блокирования «enforcing» применяется для постоянной работы СУБД для выполнения "Требований по безопасности информации к системам управления базами данных (выписка)», утвержденных Приказом ФСТЭК России № 64 от 14.04.2023 касающихся:

  • контроля целостности;

  • ограничения программной среды.

Изменения в конфигурацию СУБД и в режим работы пользователей должны быть санкционированы администратором СУБД.

Включение режима блокировки целесообразно при совместной работе компонентов «ja_CSum» и «SecurityProfile».

Компонент «ja_CSum» выполняет контроль целостности, а при выявленных нарушениях вызывает компонент «SecurityProfile» для блокирования пользователей. Ограничение программной среды компонентом выполняется путем:

  • разрешения или запрета установки расширений из списка, разрешенного ПО;

  • запрета установки расширений, не входящих в список разрешенного ПО.

Компонент «SecurityProfile» ограничивает программную среду СУБД, перехватывая выполнение команд CREATE FUNCTION / CREATE PROCEDURE.

Установка режима блокирования «enforcing» выполняется SQL-командой:

alter system set ja_csum.action_mode = 'enforcing';

Проверка файлов с КС​

Существует функциональная возможность проверки КС файлов. Для осуществления такой проверки потребуется:

  • в директории файлов контрольных сумм (параметр ja_csum.work_dir) создать дополнительный файл в формате *.csv;

  • внешними средствами рассчитать КС по алгоритму MD5;

  • заполнить данными созданный файл по требуемому формату.

При запланированной проверке КС компонент прочитает все файлы *.csv, находящиеся в директории, и запишет события безопасности.

Важная информация

Проверка файлов ОС имеет ограничение, в текущей реализации не реализован механизм пересчета КС.

При запуске функции «ja_csum.fill_list» компонент перезапишет файл «checksums.csv», а остальные файлы оставит без изменений.

Ограничения на одновременный запуск создания/перерасчета и проверки КС​

В компоненте «ja_CSum» применяется ограничение на одновременный запуск функций создания/перерасчета (fill_list()) и проверки (check_now()) файлов КС. Также ограничению подвергаются одновременные запуски нескольких указанных функций.

В случае, если уже выполняется одна из указанных функций, то новая запускаемая функция прерывается, а в журнал событий СУБД выводится сообщение:

ja_csum * [started_function] event * the function [running_function] is already running. please wait until the function completes

Где [started_function] – название запускаемой функции, а [running_function] – функция, выполняемая в данный момент.

Пример сообщения в журнале событий СУБД:

ja_csum * fill_list event * the function check_now is already running. please wait until the function completes

Данные ограничения также могут возникать в том случае, если администратор СУБД запускает вручную одну из функций создания/перерасчета и проверки КС параллельно с уже автоматически запущенными.

Управление перечнем файлов конфигурации СУБД для контроля КС​

В составе компонента «ja_Csum» предусмотрена служебная таблица param_conf, предназначенная для хранения абсолютных путей к файлам конфигураций, для которых необходимо рассчитывать и контролировать КС.

Таблица param_conf создаётся в схеме ja_csum при установке расширения ja_csum.

При установке расширения ja_csum в таблицу param_conf автоматически добавляются записи, соответствующие основным конфигурационным файлам СУБД:

  • /var/lib/jatoba/18/data/postgresql.conf

  • /var/lib/jatoba/18/data/postgresql.auto.conf

  • /var/lib/jatoba/18/data/pg_hba.conf

  • /var/lib/jatoba/18/data/pg_ident.conf

Управление перечнем файлов осуществляется как через функции расширения ja_csum, так и непосредственно с помощью DML-операций.

Дополнительная информация

Выполнение функций show_param_conf, add_param_conf, delete_param_conf доступно только владельцу расширения ja_csum или суперпользователю. Выполнение функции для роли PUBLIC запрещено! При отсутствии прав на выполнение функций будет выведено сообщение:

ОШИБКА: нет доступа к схеме ja_csum

При необходимости администратор может явно предоставить права на выполнение функций другим пользователям с помощью команды GRANT.

Все операции, связанные с добавлением и удалением записей, журналируются стандартными средствами СУБД «Jatoba».

При вставке записей вручную (через INSERT) значение столбца id формируется автоматически. Попытки явно указать значение id приводят к ошибке, за исключением случая использования переопределения OVERRIDING SYSTEM VALUE.

ПРЕДУПРЕЖДЕНИЕ: cannot delete pre-installed record with id 1

Ручное редактирование таблицы param_conf​

Администратор имеет возможность непосредственно выполнять операции INSERT, UPDATE, DELETE над таблицей param_conf (при условии наличия соответствующих привилегий). При ручном редактировании:

  • для вставки новых записей необходимо использовать DEFAULT для столбца id (или указать OVERRIDING SYSTEM VALUE при явном задании значения). Компонент «ja_CSum» автоматически назначает идентификаторы, начиная с 100;

  • проверка существования файла и доступности для чтения не выполняется в момент DML-операции (например при обновлении). Такая проверка откладывается до момента фактического использования записи (например, при расчёте КС). Если файл отсутствует или недоступен, это будет расцениваться как нарушение целостности данных, и соответствующее сообщение будет занесено в журнал;

  • при удалении записей через DELETE ограничений на удаление предустановленных записей нет (в отличие от функции delete_param_conf()), однако удаление таких записей может повлиять на корректную работу расширения и не рекомендуется.

Пример вставки новой записи в таблицу param_conf с использованием DML операции:

INSERT INTO ja_csum.param_conf VALUES (default, '/var/lib/jatoba/example.conf');

Перерасчет и проверка КС после внесения изменений в таблицу param_conf​

После добавления, обновления или удаления записей в таблице param_conf необходимо выполнить перерасчет (см. п. 3.2) и проверку КС (см. п. 3.6). Без данных действий конфигурационные файлы, указанные в таблице param_conf, не будут включены в CSV-файл с КС (см. п. 3.2.1), и любая последующая проверка КС (check_now()) завершится ошибкой, сообщающей об отсутствии записи для данного файла:

WARNING: ja_csum * check_now_event * config file not in checksum: param_conf has 5 entries but checksum database is empty

При перерасчете или проверке КС компонент «ja_CSum» проверяет доступность каждого конфигурационного файла, указанного в таблице param_conf, для чтения системной учётной записью postgres. Если нет прав на чтение конфигурационного файла из таблицы param_conf будет отображено следующее сообщение:

ПРЕДУПРЕЖДЕНИЕ: ja_csum * fill_list_event * read_file_error: /var/lib/jatoba/example.conf : Отказано в доступе

ПРЕДУПРЕЖДЕНИЕ: ja_csum * fill_list_event * read_file_error: /var/lib/jatoba/example.conf : Нет такого файла или каталога

Резервное копирование файлов конфигурации при расчёте КС​

В процессе выполнения функции ja_csum.fill_list() расширение ja_csum для каждого файла, перечисленного в таблице param_conf, создаёт его резервную копию в специализированной директории внутри каталога, заданного параметром ja_csum.work_dir (см. п. 3.2.1). Это позволяет администратору при необходимости восстановить исходное состояние конфигурационных файлов до последнего успешного перерасчёта КС.

Резервные копии хранятся в следующей структуре каталогов:

<ja_csum.work_dir>/ 
  backup_configfiles/
    <id_1>/
      <имя_файла_1>
    <id_2>/
      <имя_файла_2>
...

Поддиректории с именами, соответствующими значениям id записей из таблицы param_conf, создаются отдельно для каждого файла конфигурации. В каждой поддиректории содержится копия файла конфигурации с тем же именем, что и оригинал.

Рисунок 3.34 – Структура каталога с резервными копиями конфигурационных файлов из таблицы param_conf и права доступа

При каждом вызове функции ja_csum.fill_list() расширение выполняет следующую последовательность операций, связанных с резервным копированием:

  • проверка существования директории <work_dir>/backup_configfiles. Если директория отсутствует, она создаётся с правами доступа 0700 для системного пользователя postgres. Если права не соответствуют, то расчет КС продолжается, но в журнал записывается предупреждение:
ja_csum * fill_list_event * the user postgres does not have the necessary rights to the directory <work_dir>/backup_configfiles

Если при создании директории возникает ошибка, в журнал записывается сообщение:

ja_csum * fill_list_event * error while creating the directory <work_dir>/backup_configfiles

Расчёт КС при этом продолжается.

  • аналогично для каждой записи из param_conf выполняется проверка создания и прав доступа к поддиректории <work_dir>/backup_configfiles/;

  • если все предыдущие проверки пройдены, файл конфигурации копируется в поддиректорию с замещением существующего файла (то есть каждый перерасчёт КС обновляет резервную копию). Если в процессе копирования возникает ошибка (например, недоступность исходного файла, ошибка записи), в журнал записывается сообщение:

ja_csum * fill_list_event * error while backing up the file <путь_и_имя_файла> to directory <work_dir>/backup_configfiles/<id>

Все операции резервного копирования выполняются после расчёта КС каждого файла, но до сохранения результатов в файл «fs_checksums__.csv». Таким образом, резервные копии соответствуют состоянию файлов на момент перерасчёта КС.

Для синхронизации структуры каталогов резервных копий с текущим содержимым таблицы param_conf применяется функция ja_csum.cleanup_backup_configfiles(). Данная функция предназначена для удаления всех поддиректорий внутри <work_dir>/backup_configfiles/, имена которых являются числовыми значениями и которые отсутствуют в таблице param_conf в виде записей с соответствующим id.

Дополнительная информация

При ручном удалении записей из param_conf (через DELETE) директории с резервными копиями не удаляются автоматически – для этого необходимо вызывать cleanup_backup_configfiles() после удаления.

Функция ja_csum.cleanup_backup_configfiles() предназначена для ручного вызова администратором после удаления записей из param_conf (например, через delete_param_conf или DELETE), чтобы очистить файловую систему от устаревших резервных копий.

Дополнительная информация

Удаляются только директории с числовыми именами. Директории, имеющие имена, отличные от чисел (например, временные или служебные), игнорируются.

Журналирование событий изменения конфигурационных файлов​

В процессе проверки КС конфигурационных файлов, выполняемой функцией ja_csum.check_now(), компонент «ja_CSum» не только выявляет факт изменения файла, но и формирует детализированные события о различиях между текущим содержимым файла и его резервной копией. Это позволяет администратору оперативно отслеживать, какие именно строки были добавлены, удалены или изменены, а также принимать меры в соответствии с политикой безопасности.

При вызове check_now() в первую очередь выполняется проверка файла fs_checksums__.csv, расположенного в каталоге, указанном параметром ja_csum.work_dir (см. п. 3.2.1). При успешном прохождении проверки выполняется расчет текущих КС для всех файлов, перечисленных в таблице param_conf, и сравнение их с сохранёнными значениями из CSV-файла.

Для выявления конкретных изменений используется метод построчного сравнения файлов. Этот метод даёт наглядное представление о различиях, особенно в случае, когда структура файла не предполагает частых вставок/удалений в середине. Рекомендуется избегать произвольного удаления строк в конфигурационных файлах, чтобы минимизировать число ложных срабатываний при сравнении.

После каждого обнаруженного различия компонент «ja_CSum» записывает сообщение в журнал с уровнем WARNING.

В расширении ja_csum определены следующие параметры, влияющие на процесс формирования событий:

  • ja_csum.log_format (значения 'standard', 'ja_seceventlog1', по умолчанию 'standard');

Параметр ja_csum.log_format определяет при записи в журнал формат сообщений об изменениях в конфигурационных файлах. При значении 'standard' сообщения записываются в журнал в кратком виде. При значении 'ja_seceventlog1' дополнительно формируются структурированные записи для интеграции с компонентом «ja_seceventlog».

  • ja_csum.max_config_event (значения от 1 до максимального целого, по умолчанию 1).

Параметр ja_csum.max_config_event определяет максимальное количество сообщений об изменениях, которые будут записаны в журнал для одного конфигурационного файла в рамках одного вызова функции check_now(). Это позволяет ограничить объём журнала при наличии большого числа различий. После достижения указанного предела сравнение для данного файла прекращается.

Формат записи в журнал зависит от значения параметра ja_csum.log_format:

  • если log_format = 'standard' (значение по умолчанию), сообщение имеет вид:
ja_csum * check_now_event * changes are detected in file %s, line %d
  • если log_format = 'ja_seceventlog1', помимо стандартного сообщения, в журнал записывается структурированное сообщение в формате, совместимом с расширением ja_seceventlog:
{

"secEventFileNameConfig":"<полный путь и название изменённого файла>",

"secEventFileNameConfigBackup":"<work_dir>/backup_configfiles/< id>/<имя файла>",

"secEventParameterStringOld":"<значение строки из резервной копии>",

"secEventParameterStringNew":"<значение строки из текущего файла>",

"secEventFileConfigLine":<номер строки в текущем файле>,

"secEventFileConfigBackupLine":<номер строки в резервной копии>

}

Дополнительная информация

Формат ja_seceventlog1 используется только при обнаружении изменений (несовпадении КС). В случае успешной проверки (все КС совпадают) записи в этом формате не создаются – в журнал попадают только стандартные сообщения о завершении работы check_now().

ДЕЙСТВИЯ АДМИНИСТРАТОРА СУБД ПРИ ИЗМЕНЕНИИ ЦЕЛОСТНОСТИ СУБД​

Установленные компоненты «ja_CSum» и «SecurityProfile» при нарушении контроля целостности и ограничения программной среды СУБД в соответствии с "Требованиями по безопасности информации к системам управления базами данных (выписка)» заблокируют пользователей СУБД, что в условиях промышленной эксплуатации СУБД является негативным последствием.

Чтобы избежать негативных последствий выполните последовательность действий, приведенную ниже.

Например, требуется внести санкционированные изменения в конфигурационные файлы СУБД. Порядок действий должен быть следующим:

  1. Перевести компонент «ja_CSum» в режим информирования «permissive» (см. п. 3.7.1).

  2. Отключить режим периодической проверки (см. п. 3.5).

  3. Внести требуемые изменения.

  4. Обновить файлы с контрольными суммами (см. п. 3.2).

  5. Перезагрузить СУБД.

  6. Войти в СУБД от имени и с правами Администратора СУБД.

  7. Перевести компонент «ja_CSum» в режим блокирования «enforcing» (см. п. 3.7.2).

  8. Включить режим периодической проверки (см. п. 3.5).

Для контроля над работой компонентов «ja_CSum», «SecurityProfile» и в целом СУБД, целесообразно воспользоваться функциональными возможностями раздела «Уведомления» (Notifications) компонента пользовательского веб-интерфейса для администраторов «Jatoba data safe».

ВЗАИМОДЕЙСТВИЕ С ДРУГИМИ КОМПОНЕНТАМИ СУБД JATOBA​

Взаимодействие с компонентом «jaDog»​

Установка компонента «ja_CSum» на кластере «jaDog»​

Установка компонента «ja_CSum» на существующем отказоустойчивом кластере «jaDog» выполняется в следующей последовательности:

  1. На существующем отказоустойчивом кластере «jaDog» необходимо установить пакет (см. п. 2.1) на все узлы.

  2. Затем в конфигурационном файле postgresql.conf на каждом узле отказоустойчивого кластера указать следующие параметры:

shared_preload_libraries = 'ja_csum'
# Добавить в конец файла в секцию CUSTOMIZED OPTIONS: 
ja_csum.db_name = 'postgres'
ja_csum.action_mode = 'permissive' 
ja_csum.auto_create_extension = off 
ja_csum.check_auto = false
  1. Сохранить конфигурационный файл postgresql.conf и выполнить перезапуск СУБД на каждом узле, например с помощью консольной утилиты jadog_ctl (входит в состав компонента «jaDog»):
restart dbs cluster
  1. После перезапуска СУБД подключиться к консольной утилите jadog_ctl и проверить состояние узлов кластера:
cluster

  1. После этого выполнить установку расширения ja_csum на главных узлах кластера согласно п. 2.3.

  2. Выполнить перерасчет КС при помощи функции ja_csum.fill_list (см. п.3.2).

  3. Выполнить проверку КС при помощи функции ja_csum.check_now (см. п. 3.6).

  4. На всех узлах кластера включить автоматическую проверку КС:

ja_csum.check_auto = true

  1. Выполнить перезапуск СУБД на каждом узле с помощью консольной утилиты jadog_ctl (см. выше).

  2. На всех узлах кластера выполнить создание новых КС при помощи функции ja_csum.fill_list (см. п.3.2).

  3. Выполнить перезапуск СУБД на каждом узле с помощью консольной утилиты jadog_ctl (см. выше).

На этом этапе установка компонента «ja_CSum» на существующем отказоустойчивом кластере «jaDog» считается выполненной успешно.

При возникновении проблем необходимо проверять журнал событий СУБД на сообщения с описанием возникших ошибок.

Временное отключение контроля КС при изменении конфигурации кластера «jaDog»​

В случае разворачивания или изменении параметров/состава кластера «jaDog» в конфигурационном файле postgresql.conf необходимо временно устанавливать следующие параметры:

ja_csum.action_mode = 'permissive' 
ja_csum.check_auto = off

После того как необходимые изменения параметров/состава кластера «jaDog» выполнены необходимо вернуть штатные значения параметров:

ja_csum.action_mode = 'enforcing' 
ja_csum.check_auto = on

и выполнить перерасчет КС при помощи функции ja_csum.fill_list (см. п.3.2).

Особенности запуска расчета и/или проверки КС на узлах отказоустойчивого кластера «jaDog»​

При запуске процедур расчета КС файлов и/или их проверки при совместной эксплуатации с компонентом «jaDog» выполняется определение какая роль узла (главный или резервный) в отказоустойчивом кластере. В зависимости от роли узла процедуры расчета КС файлов и их проверки имеются особенности, указанные далее.

  1. Расчет КС файлов СУБД на главном узле кластера.

Выполнение функции fill_list() на главном узле кластера производится для всех объектов СУБД (перечислены в разделе 3). Запись файлов с рассчитанными КС конфигурационных файлов СУБД при этом производится в каталог, указанный в параметре ja_csum.work_dir (см. п. 2.3).

Расчет КС бинарных объектов и объектов СУБД производится в служебные таблицы компонента (см. п. 3.2.2). В отказоустойчивом кластере компонента «jaDog» данные служебные таблицы автоматически реплицируются с главного узла на резервные.

  1. Расчет КС файлов СУБД на резервном узле кластера.

Выполнение функции fill_list() на резервном узле кластера производится только для конфигурационных файлов СУБД. Запись файлов с рассчитанными КС конфигурационных файлов СУБД производится точно также как и на главном узле кластера.

Расчет КС бинарных объектов и объектов СУБД при выполнении функции fill_list() на резервном узле кластера не производится, так как таблицы, содержание данную информацию, реплицируются на резервный узел с главного.

Дополнительная информация

Рассчитанные КС конфигурационных файлов СУБД на главном и резервных узлах будут отличаться.

  1. Проверка КС файлов СУБД на главном и резервных узлах кластера не отличается и производится в соответствии с тем как это приведено в п. 3.6.
Важная информация

В том случае, если в кластере компонент «ja_CSum» функционирует совместно с компонентом «SecurityProfile», и компонент «ja_CSum» эксплуатируется в режиме блокирования (ja_csum.action_mode=enforcing, см. п. 3.7.2), то имеются отличия в вызове функций безопасности компонента «SecurityProfile».

На главном узле кластера «jaDog» компонент «ja_CSum» вызовет функцию securityprofile.suspend_user(), которая записывает информацию о блокировке пользователей в служебные таблицы компонента «SecurityProfile». После этого вызывается функция securityprofile.terminate_backend(), которая принудительно прерывает сессии пользователей на главном узле кластера.

На резервном узле кластера «jaDog» ja_csum вызовет только функцию securityprofile.terminate_backend(), так как резервные узлы работают с СУБД в режиме чтения (read only).

Действия на узлах кластера при обнаружении изменений в конфигурационных файлах СУБД​

Если при проверке (см. п. 3.14.5) выявлены изменения в конфигурационном файле (несовпадение КС или различия в содержимом), дальнейшие действия определяются параметром ja_csum.action_mode (см. п. 3.7) и наличием расширения securityprofile.

  • если ja_csum.action_mode = 'enforcing' и расширение securityprofile установлено, то на главном узле выполняются разрыв сессий (securityprofile.terminate_backend) и блокировка пользователей (securityprofile.suspend_users). На резервных узлах выполняется только разрыв активных сессий пользователей.

  • если ja_csum.action_mode = 'permissive' или расширение securityprofile не установлено, никаких дополнительных действий не предпринимается – проверка КС завершается с выдачей предупреждений в журнал.

Аутентификационная информация — информация, используемая при аутентификации субъекта доступа или объекта доступа.

Аутентификация – действия по проверке подлинности субъекта доступа и/или объекта доступа, а также по проверке принадлежности субъекту доступа и/или объекту доступа предъявленного идентификатора доступа и аутентификационной информации (ГОСТ Р 58833-2020).

Администратор СУБД – субъект доступа, выполняющий административные функции в СУБД и наделенный правами:

  • создавать учетные записи пользователей системы управления базами данных;

  • модифицировать, блокировать и удалять учетные записи пользователей системы управления базами данных;

  • назначать права доступа пользователям системы управления базами данных к объектам доступа системы управления базами данных;

  • управлять конфигурацией системы управления базами данных;

  • создавать, подключать базы данных.

Администратор СУБД имеет атрибут SUPERUSER и/или обладает системной учетной записью «postgres».

Администратор БД – субъект доступа, выполняющий административные функции в БД и наделенный правами:

  • создавать учетные записи пользователей базы данных;

  • модифицировать, блокировать и удалять учетные записи пользователей базы данных;

  • управлять конфигурацией базы данных;

  • назначать права доступа пользователям базы данных (пользователей информационной системы) к объектам доступа базы данных;

  • создавать резервные копии базы данных и восстанавливать базу данных из резервной копии;

  • создавать, модифицировать и удалять процедуры (программный код), хранимые в базе данных.

Администратор БД имеет атрибут CREATEROLE, и возможные атрибуты BYPASSRLS, REPLICATION, а также прочие системные привилегии относительно БД, кроме атрибута CREATEDB.

Безусловная блокировка пользователя – это ограничение пользователя в возможности устанавливать новую сессию с СУБД. Безусловная блокировка имеет приоритет над ограничениями, накладываемыми парольными политикам (блокировка вследствие истечения срока действия пароля, временные блокировки при исчерпании попыток ввода пароля и т.п.), применяется независимо от них и не зависит от применяемого метода аутентификации пользователей. Снятие безусловной блокировки не снимает блокировок по парольным политикам и наоборот.

Завершение сессии пользователя – принудительное завершение открытой сессии пользователя с БД/СУБД в заданном режиме.

Пользователь БД - субъект доступа, имеющий доступ к ограниченному перечню БД и объектов БД. Имеющий следующий набор привилегий:

  • создавать и манипулировать объектами доступа БД (таблица, запись или столбец, поле, представление и иные объекты доступа);

  • выполнять процедуры (программный код), хранимые в БД. Пользователь БД имеет обязательный атрибут LOGIN.

Пользователь СУБД – см. «Пользователь БД». Для СУБД эти понятия идентичны. СУБД не разграничивает пользователей по отдельным БД. Все пользователи общие, доступ к отдельным БД определяется настройками доступа.

Режим завершения – способ завершения открытой сессии пользователя с БД/СУБД работающий в режимах:

  • smart – запрещает пользователю выполнение новых транзакций, ожидает завершения текущих транзакций, после этого отключает пользователя;

  • fast (режим по умолчанию) – все активные транзакции откатываются, а пользователь принудительно отключается;

  • immediate – пользователь принудительно отключается без ожидания и непосредственного отката транзакций

Роль – субъект доступа в БД/СУБД, наделенный определенным набором привилегий (чаще всего употребляется как обобщение группы пользователей для выполнения определенного набора действий в БД/СУБД).
