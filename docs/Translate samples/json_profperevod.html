[]{#id-1.5.7.22.2 .indexterm}[]{#id-1.5.7.22.3 .indexterm}

Типы данных JSON предназначены для хранения данных в формате JSON (JavaScript Object Notation), как описано в RFC 7159{.ulink target="_top"}. Такие данные также можно хранить в виде text{.type}, но типы JSON имеют преимущество: они гарантируют, что каждое сохраненное значение соответствует правилам JSON. Кроме того, для данных, хранящихся в этих типах, доступны различные специализированные функции и операторы JSON (см. Раздел 9.16){.xref}.

[PostgreSQL]{.productname} предлагает два типа данных для хранения JSON: json{.type} и jsonb{.type}. Для реализации эффективных механизмов запросов к этим типам данных [PostgreSQL]{.productname} также предоставляет тип jsonpath{.type}, описанный в Разделе 8.14.7{.xref}.

Типы json{.type} и jsonb{.type} принимают [практически]{.emphasis} идентичные наборы значений на вход. Основное практическое различие заключается в эффективности. Тип json{.type} хранит точную копию входного текста, который функциям обработки приходится повторно разбирать при каждом выполнении, тогда как jsonb{.type} хранит данные в декомпонованном бинарном формате. Это делает ввод данных немного медленнее из-за дополнительных затрат на преобразование, но обработка происходит значительно быстрее, так как не требует повторного разбора. Кроме того, jsonb{.type} поддерживает индексацию, что может стать существенным преимуществом.

Поскольку тип json{.type} хранит точную копию входного текста, он сохраняет семантически незначимые пробелы между токенами, а также порядок ключей в JSON-объектах. Кроме того, если JSON-объект в значении содержит одинаковый ключ более одного раза, сохраняются все пары ключ/значение. (Обрабатывающие функции считают последнее значение актуальным.) В отличие от этого, jsonb{.type} не сохраняет пробелы, порядок ключей объекта или дублирующиеся ключи. Если во входных данных указаны дублирующиеся ключи, сохраняется только последнее значение.

Как правило, большинству приложений следует хранить JSON-данные в формате jsonb{.type}, если только нет узкоспециализированных требований, таких как унаследованные допущения о порядке ключей в объекте.

RFC 7159 предписывает, что строки JSON должны кодироваться в UTF-8. Следовательно, JSON-типы не могут строго соответствовать спецификации JSON, если кодировка базы данных не является UTF-8. Попытки напрямую включить символы, которые не могут быть представлены в текущей кодировке базы данных, завершатся ошибкой. И наоборот, символы, которые могут быть представлены в кодировке базы данных, но не в UTF-8, будут разрешены.

RFC 7159 допускает наличие в JSON-строках Unicode-последовательностей, обозначаемых как \uXXXX{.literal}. Во входной функции для типа json{.type} Unicode-экранирование разрешено независимо от кодировки базы данных и проверяется только на синтаксическую корректность (то есть что после \u{.literal} следуют четыре шестнадцатеричные цифры). Однако входная функция для jsonb{.type} более строгая: она запрещает Unicode-экранирование для символов, которые не могут быть представлены в кодировке базы данных. Тип jsonb{.type} также отклоняет последовательность \u0000{.literal} (поскольку она не может быть представлена в типе text{.type}[PostgreSQL]{.productname}) и требует, чтобы любые использования суррогатных пар Unicode для обозначения символов вне базовой многоязыковой плоскости Unicode (BMP) были корректными. Допустимые Unicode-последовательности преобразуются в эквивалентные одиночные символы для хранения, включая объединение суррогатных пар в один символ.

::: note

Примечание​

Многие функции обработки JSON, описанные в Разделе 9.16{.xref} преобразуют символы Unicode в обычные символы и будут выбрасывать те же типы ошибок, описанные ранее, даже если их входные данные имеют тип json{.type}, а не jsonb{.type}. Тот факт, что функция ввода json{.type} не выполняет эти проверки, может рассматриваться как исторический артефакт, хотя она позволяет просто хранить (без обработки) символы Unicode JSON в кодировке базы данных, которая не поддерживает представленные символы. :::

При преобразовании текстового ввода JSON в тип jsonb{.type}, примитивные типы, описанные в RFC 7159, эффективно отображаются на собственные типы [PostgreSQL]{.productname}, как показано в Таблице 8.23{.xref}. Поэтому существуют некоторые незначительные дополнительные ограничения на то, что является допустимыми данными типа jsonb{.type}, которые не применяются к типу json{.type} или к JSON в абстрактном смысле, соответствующие ограничениям на то, что может быть представлено базовым типом данных. В частности, jsonb{.type} будет отклонять числа, выходящие за пределы диапазона числовых данных типа  [PostgreSQL]{.productname} numeric{.type}, в то время как json{.type} этого не делает. Такие ограничения, определенные реализацией, разрешены RFC7159. Однако на практике такие проблемы гораздо более вероятно возникают в других реализациях, так как обычно примитивный тип числа{.type} JSON представляется двойной точностью с плавающей запятой IEEE 754 (что явно предусмотрено и разрешено RFC 7159). При использовании JSON в качестве формата обмена данными с такими системами следует учитывать опасность потери числовой точности по сравнению с данными, изначально сохраненными в [PostgreSQL]{.productname}.

Наоборот, как указано в таблице, существуют некоторые незначительные ограничения на формат ввода примитивных типов JSON, которые не применяются к соответствующим типам [PostgreSQL]{.productname}.

8.14.1. Синтаксис ввода и вывода JSON #{.id_link}​

:::

Синтаксис ввода/вывода для типов данных JSON соответствует спецификации в RFC 7159.

Следующие выражения json{.type} (или jsonb{.type}) являются допустимыми:

-- Простое скалярное/примитивное значение
-- Примитивные значения могут быть числами, строками в кавычках, true, false или null
SELECT '5'::json;

-- Массив из нуля или более элементов (элементы могут быть разных типов)
SELECT '[1, 2, "foo", null]'::json;

-- Объект, содержащий пары ключ-значение
-- Обратите внимание, что ключи объектов всегда должны быть строками в кавычках
SELECT '{"bar": "baz", "balance": 7.77, "active": false}'::json;

-- Массивы и объекты могут быть вложены друг в друга произвольным образом
SELECT '{"foo": [true, "bar"], "tags": {"a": 1, "b": null}}'::json;

Как уже упоминалось ранее, когда значение JSON вводится и затем выводится без дополнительной обработки, json{.type} выводит тот же текст, который был введен, в то время как jsonb{.type} не сохраняет семантически незначимые детали, такие как пробелы. Например, обратите внимание на различия здесь:

SELECT '{"bar": "baz", "balance": 7.77, "active":false}'::json;
                      json
-------------------------------------------------
 {"bar": "baz", "balance": 7.77, "active":false}
(1 строка)

SELECT '{"bar": "baz", "balance": 7.77, "active":false}'::jsonb;
                      jsonb
--------------------------------------------------
 {"bar": "baz", "active": false, "balance": 7.77}
(1 строка)

Одна семантически незначимая деталь, которую стоит отметить, заключается в том, что в типе jsonb{.type} числа будут выводиться в соответствии с поведением базового типа numeric{.type}. На практике это означает, что числа, введенные с использованием обозначения E{.literal}, будут выводиться без него, например:

SELECT '{"reading": 1.230e-5}'::json, '{"reading": 1.230e-5}'::jsonb;
         json          |          jsonb
-----------------------+-------------------------
 {"reading": 1.230e-5} | {"reading": 0.00001230}
(1 строка)

Однако, jsonb{.type} сохранит конечные дробные нули, как видно в этом примере, даже если они семантически несущественны для целей, таких как проверка равенства.

Для списка встроенных функций и операторов, доступных для создания и обработки значений JSON, см. Раздел 9.16{.xref}. :::

8.14.2. Проектирование JSON-документов #{.id_link}​

:::

Представление данных в формате JSON может быть гораздо более гибким, чем традиционная реляционная модель данных, что является привлекательным в средах, где требования постоянно меняются. Возможно сосуществование и взаимодополняемость обоих подходов в рамках одного приложения. Однако, даже для приложений, где требуется максимальная гибкость, рекомендуется, чтобы JSON-документы имели относительно фиксированную структуру. Обычно структура не является обязательной (хотя возможно декларативное применение некоторых бизнес-правил), но наличие предсказуемой структуры упрощает написание запросов, которые полезно резюмируют набор ["[документов]{.quote}"]{.quote} (данных) в таблице.

JSON-данные подчиняются тем же правилам контроля параллелизма, что и любой другой тип данных при хранении в таблице. Хотя хранение больших документов является практичным, имейте в виду, что любое обновление приобретает блокировку на уровне строки для всей строки. Рассмотрите возможность ограничения размера JSON-документов для уменьшения конкуренции блокировок между обновляющими транзакциями. Идеально JSON-документы должны представлять собой атомарные данные, которые бизнес-правила определяют как неразделимые на более мелкие данные, которые могут быть изменены независимо. :::

8.14.3. jsonb{.type}  операторы Containment и Existence #{.id_link}​

:::

[]{#id-1.5.7.22.17.2 .indexterm}[]{#id-1.5.7.22.17.3 .indexterm}

Тестирование containment (содержимого) является важной возможностью jsonb{.type}. Для типа json{.type} нет аналогичного набора функций. Проверка содержимого определяет, содержит ли один документ jsonb{.type} другой. Эти примеры возвращают true, за исключением указанных случаев:

-- Простые скалярные/примитивные значения содержат только идентичное значение:
SELECT '"foo"'::jsonb @> '"foo"'::jsonb;

-- Массив справа содержится в массиве слева:
SELECT '[1, 2, 3]'::jsonb @> '[1, 3]'::jsonb;

-- Порядок элементов в массиве не имеет значения, поэтому следующее выражение также верно:
SELECT '[1, 2, 3]'::jsonb @> '[3, 1]'::jsonb;

-- Повторяющиеся элементы массива также не имеют значения:
SELECT '[1, 2, 3]'::jsonb @> '[1, 2, 2]'::jsonb;

-- Объект с одной парой в правой части содержится
-- внутри объекта слева:
SELECT '{"product": "PostgreSQL", "version": 9.4, "jsonb": true}'::jsonb @> '{"version": 9.4}'::jsonb;

-- Массив справа не  считается входящим в
--  массив слева, даже если похожий массив вложен в него:
SELECT '[1, 2, [1, 3]]'::jsonb @> '[1, 3]'::jsonb;  -- возвращает false

-- Однако при добавлении уровня вложенности проблема локализуется:
SELECT '[1, 2, [1, 3]]'::jsonb @> '[[1, 3]]'::jsonb;

-- Аналогично, здесь не проверяется содержание.
SELECT '{"foo": {"bar": "baz"}}'::jsonb @> '{"bar": "baz"}'::jsonb;  -- возвращает false

-- Содержит ключ верхнего уровня и пустой объект:
SELECT '{"foo": {"bar": "baz"}}'::jsonb @> '{"foo": {}}'::jsonb;

Общий принцип заключается в том, что содержащийся объект должен соответствовать структуре и содержанию данных содержащего объекта, возможно после отбрасывания некоторых несоответствующих элементов массива или пар ключ/значение объекта из содержащего объекта. Но помните, что порядок элементов массива не имеет значения при сопоставлении содержимого, и дублирующиеся элементы массива эффективно считаются только один раз.

В качестве особого исключения из общего принципа, что структуры должны совпадать, массив может содержать примитивное значение:

-- Этот массив содержит примитивное строковое значение:
SELECT '["foo", "bar"]'::jsonb @> '"bar"'::jsonb;

-- Это исключение не является взаимным  -- здесь сообщается об отсутствии содержания:
SELECT '"bar"'::jsonb @> '["bar"]'::jsonb;  -- возвращает false

jsonb{.type} также имеет оператор existence, который является вариацией на тему содержания: он проверяет, появляется ли строка (заданная как значение text{.type}) в качестве ключа объекта или элемента массива на верхнем уровне значения jsonb{.type}. Эти примеры возвращают true, за исключением указанных случаев:

-- Строка существует как элемент массива:
SELECT '["foo", "bar", "baz"]'::jsonb ? 'bar';

-- Строка существует как ключ объекта:
SELECT '{"foo": "bar"}'::jsonb ? 'foo';

-- Значения объектов не учитываются:
SELECT '{"foo": "bar"}'::jsonb ? 'bar';  -- возвращает false

-- Как и в случае с проверкой содержания, проверка существования должна совпадать на верхнем уровне:
SELECT '{"foo": {"bar": "baz"}}'::jsonb ? 'bar'; -- возвращает false

-- Строка считается существующей, если она соответствует примитивной JSON-строке:
SELECT '"foo"'::jsonb ? 'foo';

JSON-объекты лучше подходят для проверки наличия или содержания, когда вовлечено много ключей или элементов, потому что, в отличие от массивов, они внутренне оптимизированы для поиска и не требуют линейного поиска.

::: tip

Подсказка​

Поскольку JSON-контейнеры являются вложенными, соответствующий запрос может пропустить явный выбор подобъектов. Например, предположим, что у нас есть столбец doc{.structfield}, содержащий объекты на верхнем уровне, большинство из которых содержат поля tags{.literal}, содержащие массивы подобъектов. Этот запрос находит записи, в которых подобъекты, содержащие и "term":"paris"{.literal}, и "term":"food"{.literal}, появляются, игнорируя любые такие ключи вне массива tags{.literal}:

SELECT doc->'site_name' FROM websites
  WHERE doc @> '{"tags":[{"term":"paris"}, {"term":"food"}]}';

То же самое можно сделать, скажем,

SELECT doc->'site_name' FROM websites
  WHERE doc->'tags' @> '[{"term":"paris"}, {"term":"food"}]';

но такой подход менее гибкий и часто менее эффективный.

С другой стороны, оператор существования JSON не является вложенным: он будет искать только указанный ключ или элемент массива на верхнем уровне значения JSON. :::

Различные операторы содержания и существования, а также все остальные операторы и функции JSON документированы в Разделе 9.16{.xref}. :::

::: {#JSON-INDEXING .sect2} ::: titlepage

8.14.4.  Индексирование jsonb{.type} #{.id_link}​

:::

[]{#id-1.5.7.22.18.2 .indexterm}

GIN индексы могут быть использованы для эффективного поиска ключей или пар ключ/значение, встречающихся в большом количестве документов jsonb{.type} (датумов). Предоставляются два ["[класса операторов]{.quote}"]{.quote} GIN, предлагающих различные компромиссы между производительностью и гибкостью.

Класс операторов GIN по умолчанию для jsonb{.type} поддерживает запросы с использованием операторов проверки наличия ключа ?{.literal}, ?|{.literal} и ?&{.literal}, оператора содержания @>{.literal} и операторов сопоставления jsonpath{.type} @?{.literal} и @@{.literal}. (Подробнее о семантике, реализуемой этими операторами, см. Таблице 9.46{.xref}). Пример создания индекса с использованием этого класса операторов:

CREATE INDEX idxgin ON api USING GIN (jdoc);

Нестандартный класс операторов jsonb_path_ops{.literal} не поддерживает операторы проверки наличия ключа, но поддерживает операторы  @>{.literal}, @?{.literal}и @@{.literal}. Пример создания индекса с использованием этого класса операторов:

CREATE INDEX idxginp ON api USING GIN (jdoc jsonb_path_ops);

Рассмотрим пример таблицы, которая хранит JSON-документы, полученные из стороннего веб-сервиса, с задокументированной схемой определения. Типичный документ выглядит так:

{
    "guid": "9c36adc1-7fb5-4d5b-83b4-90356a46061a",
    "name": "Angela Barton",
    "is_active": true,
    "company": "Magnafone",
    "address": "178 Howard Place, Gulf, Washington, 702",
    "registered": "2009-11-07T08:53:22 +08:00",
    "latitude": 19.793713,
    "longitude": 86.513373,
    "tags": [
        "enim",
        "aliquip",
        "qui"
    ]
}

Мы храним эти документы в таблице с именем api{.structname}, в столбце jsonb{.type} с именем jdoc{.structfield}. Если на этом столбце создан индекс GIN, запросы, подобные следующим, могут использовать индекс:

-- Найти документы, в которых ключ "company" имеет значение "Magnafone"
SELECT jdoc->'guid', jdoc->'name' FROM api WHERE jdoc @> '{"company": "Magnafone"}';

Однако индекс не может использоваться для запросов, подобных следующим, потому что, хотя оператор ?{.literal}является индексируемым, он не применяется непосредственно к индексированному столбцу jdoc{.structfield}:

-- Найти документы, в которых ключ "tags" содержит ключ или элемент массива "qui"
SELECT jdoc->'guid', jdoc->'name' FROM api WHERE jdoc -> 'tags' ? 'qui';

Все же, с правильным использованием индексов выражений, вышеприведенный запрос может использовать индекс. Если часто выполняются запросы для определенных элементов в ключе "tags"{.literal}, то определение индекса вот таким образом может быть целесообразным:

CREATE INDEX idxgintags ON api USING GIN ((jdoc -> 'tags'));

Теперь, предложение WHERE{.literal} jdoc -> 'tags' ? 'qui'{.literal} будет распознано как применение индексируемого оператора ?{.literal} к индексированному выражению jdoc -> 'tags'{.literal}. (Более подробную информацию о выражениях-индексах можно найти в Разделе 11.7{.xref}).

Другой подход к запросам - это использование вложенности, например:

-- Найти документы, в которых ключ "tags" содержит элемент массива "qui"
SELECT jdoc->'guid', jdoc->'name' FROM api WHERE jdoc @> '{"tags": ["qui"]}';

Простой индекс GIN на столбце jdoc{.structfield} может поддерживать этот запрос. Но обратите внимание, что такой индекс будет хранить копии каждого ключа и значения в столбце jdoc{.structfield}, в то время как индекс выражений из предыдущего примера хранит только данные, найденные под ключом tags{.literal}. В то время как простой подход к индексированию гораздо более гибкий (поскольку он поддерживает запросы по любому ключу), целевые индексы выражений, скорее всего, будут меньше и быстрее для поиска, чем простой индекс.

GIN-индексы также поддерживают операторы @?{.literal} и @@{.literal}, которые выполняют сопоставление jsonpath{.type}. Примеры:

SELECT jdoc->'guid', jdoc->'name' FROM api WHERE jdoc @? '$.tags[*] ? (@ == "qui")';
SELECT jdoc->'guid', jdoc->'name' FROM api WHERE jdoc @@ '$.tags[*] == "qui"';

Для этих операторов индекс GIN извлекает предложения accessors_chain{.literal} = constant из шаблона jsonpath{.type} и выполняет поиск по индексу на основе ключей и значений, указанных в этих предложениях. Цепочка аксессоров может включать .key{.literal}, [*]{.literal} и [index{.literal}]. Операторный класс jsonb_ops{.literal} также поддерживает аксессоры .*{.literal} и .**{.literal}, но операторный класс jsonb_path_ops{.literal} - нет.

Хотя класс операторов jsonb_path_ops {.literal}поддерживает только запросы с операторами  @>{.literal}, @?{.literal} и @@{.literal}, он имеет заметные преимущества производительности по сравнению с классом операторов по умолчанию jsonb_ops{.literal}. Индекс jsonb_path_ops{.literal} обычно значительно меньше, чем индекс jsonb_ops{.literal} для тех же данных, и специфичность поиска лучше, особенно когда запросы содержат ключи, которые часто встречаются в данных. Поэтому операции поиска обычно выполняются лучше, чем с классом операторов по умолчанию.

Разница между техническими индексами GIN  jsonb_ops{.literal} и jsonb_path_ops{.literal} заключается в том, что первый создает независимые элементы индекса для каждого ключа и значения в данных, в то время как второй создает элементы индекса только для каждого значения в данных. ^[7]^{.footnote} В основном, каждый элемент индекса jsonb_path_ops{.literal} представляет собой хеш-значение и ключ(и), ведущие к нему; например, для индексации {"foo": {"bar": "baz"}}{.literal} будет создан один элемент индекса, включающий все три значения  foo{.literal}, bar{.literal} и baz{.literal}. Таким образом, запрос на содержание этой структуры приведет к крайне точному поиску по индексу; однако нет никакого способа узнать, появляется ли foo{.literal} в качестве ключа. С другой стороны, индекс jsonb_ops{.literal} создаст три элемента индекса, представляющих отдельно foo{.literal}, bar{.literal}, и baz{.literal}; затем для выполнения запроса на содержание он будет искать строки, содержащие все три элемента. Хотя индексы GIN могут выполнять такой поиск с использованием оператора AND достаточно эффективно, он все равно будет менее точным и медленнее, чем эквивалентный поиск с использованием  jsonb_path_ops{.literal}, особенно если имеется очень большое количество строк, содержащих любой из трех элементов индекса.

Одним из недостатков подхода jsonb_path_ops{.literal} является отсутствие индексных записей для JSON-структур, не содержащих значения, например, {"a": {}}{.literal}. Если требуется поиск документов, содержащих такую структуру, потребуется полное сканирование индекса, что довольно медленно. Поэтому jsonb_path_ops{.literal} не подходит для приложений, которые часто выполняют такие поиски.

jsonb{.type} также поддерживает индексы btree{.literal} и hash{.literal}. Они обычно полезны только в том случае, если важно проверить равенство полных JSON-документов. Порядок btree{.literal} для данных типа jsonb{.type} редко представляет большой интерес, но для полноты он следующий:

Object > Array > Boolean > Number > String > null

Object with n pairs > object with n - 1 pairs

Array with n elements > array with n - 1 elements

за исключением того, что (по историческим причинам) пустой массив верхнего уровня сортируется меньше, чем  null. Объекты с равным количеством пар сравниваются в следующем порядке:

key-1, value-1, key-2 ...

Обратите внимание, что ключи объектов сравниваются в их порядке хранения; в частности, поскольку более короткие ключи хранятся перед более длинными ключами, это может привести к результатам, которые могут быть неочевидными, например:

{ "aa": 1, "c": 1} > {"b": 1, "d": 1}

Аналогично, массивы с одинаковым количеством элементов сравниваются в порядке:

element-1, element-2 ...

Примитивные значения JSON сравниваются с использованием тех же правил сравнения, что и для базового типа данных [PostgreSQL]{.productname}. Строки сравниваются с использованием сортировки базы данных по умолчанию. :::

8.14.5. Индексация jsonb{.type} #{.id_link}​

:::

Тип данных jsonb{.type} поддерживает выражения индексов в стиле массива для извлечения и изменения элементов. Вложенные значения можно указать путем цепочки выражений индексов, следуя тем же правилам, что и аргумент path{.literal} в функции jsonb_set{.literal}. Если значение jsonb{.type} является массивом, числовые индексы начинаются с нуля, а отрицательные целые числа считаются в обратном порядке от последнего элемента массива. Выражения среза не поддерживаются. Результатом выражения индекса всегда является тип данных jsonb.

UPDATE{.command} операторы могут использовать индексацию в SET{.literal} разделе для изменения значений типа jsonb{.type}. Индексные пути должны быть доступны для всех затронутых значений, насколько они существуют. Например, путь val['a']['b']['c']{.literal} может быть пройден до c{.literal}, если каждый  val{.literal}, val['a']{.literal} и val['a']['b']{.literal} являются объектами. Если val['a']{.literal} или val['a']['b']{.literal} не определены, они будут созданы как пустые объекты и заполнены по мере необходимости. Однако, если сам val{.literal} или одно из промежуточных значений определено как не объект, такой как строка, число или jsonb{.literal} null{.literal}, процесс обхода не может продолжаться, поэтому возникает ошибка и транзакция прерывается.

Пример синтаксиса индексации:

-- Извлечь значение объекта по ключу
SELECT ('{"a": 1}'::jsonb)['a'];

-- Извлечь значение вложенного объекта по цепочке ключей
SELECT ('{"a": {"b": {"c": 1}}}'::jsonb)['a']['b']['c'];

-- Извлечь элемент массива по индексу
SELECT ('[1, "2", null]'::jsonb)[1];

-- Обновить значение объекта по ключу.Обратите внимание на кавычки у '1': здесь присваивается
-- значение также должно быть типа jsonb
UPDATE table_name SET jsonb_field['key'] = '1';

-- Эта команда вызовет ошибку, если jsonb_field['a']['b'] для любой записи содержит что-либо,
-- кроме объекта.Например, значение {"a": 1} содержит числовое значение 
-- по ключу 'a'.
UPDATE table_name SET jsonb_field['a']['b']['c'] = '1';

-- Фильтрация записей с помощью WHERE и обращения по индексу.Поскольку результат
-- обращения по индексу имеет тип jsonb, сравниваемое значение также должно быть типа jsonb.
-- Двойные кавычки делают "value" также допустимой строкой jsonb.
SELECT * FROM table_name WHERE jsonb_field['key'] = '"value"';

jsonb{.type} присваивание через индексирование обрабатывает несколько крайних случаев по-разному по сравнению с jsonb_set{.literal}. Когда исходное значение jsonb{.type} равно NULL{.literal}, присваивание через индексирование будет выполняться так, как если бы это было пустое значение JSON типа (объект или массив), подразумеваемого ключом индексирования:

-- Где поле jsonb_field было NULL, теперь оно содержит {"a": 1}
UPDATE table_name SET jsonb_field['a'] = '1';

-- Где поле jsonb_field было NULL, теперь оно содержит [1].
UPDATE table_name SET jsonb_field[0] = '1';

Если для массива, содержащего недостаточное количество элементов, указан индекс, будут добавлены элементы NULL{.literal} до тех пор, пока индекс не станет доступным, и значение не сможет быть установлено.

-- Где поле jsonb_field было пустым массивом [], теперь оно содержит [null, null, 2];
-- где поле jsonb_field изменилось с [0] на [0, null, 2]
UPDATE table_name SET jsonb_field[2] = '2';

Значение jsonb{.type} будет принимать присваивания для несуществующих подскриптовых путей, пока последний существующий элемент, который будет пройден, является объектом или массивом, как это подразумевается соответствующим подскриптом (элемент, указанный последним подскриптом в пути, не проходится и может быть чем угодно). Вложенные массивы и объектные структуры будут созданы, а в первом случае заполнены null{.literal}, как указано в подскриптовом пути, пока не будет размещено присвоенное значение.

-- Где поле jsonb_field было {}, теперь оно {"a": [{"b": 1}]}.
UPDATE table_name SET jsonb_field['a'][0]['b'] = '1';

-- Где поле jsonb_field было пустым массивом [], теперь оно содержит [null, {"a": 1}]
UPDATE table_name SET jsonb_field[1]['a'] = '1';

8.14.6. Преобразования #{.id_link}​

:::

Дополнительные расширения доступны, которые реализуют преобразования для типа jsonb{.type} для различных процедурных языков.

Расширения для PL/Perl называются jsonb_plperl{.literal} и jsonb_plperlu{.literal}. Если вы их используете, значения jsonb{.type} будут отображаться на соответствующие массивы, хеши и скаляры Perl.

Расширение для PL/Python называется jsonb_plpython3u{.literal}. Если вы его используете, значения jsonb{.type} отображаются на словари, списки и скаляры Python, в зависимости от контекста.

Из этих расширений, jsonb_plperl{.literal} считается ["[trusted]{.quote}"]{.quote}, то есть его можно установить несуперпользователям, у которых есть привилегия CREATE{.literal} в текущей базе данных. Для установки остальных требуется привилегия суперпользователя. :::

8.14.7. Тип jsonpath #{.id_link}​

:::

[]{#id-1.5.7.22.21.2 .indexterm}

Тип jsonpath{.type} реализует поддержку языка выражения пути SQL/JSON в [PostgreSQL]{.productname} для эффективного запроса данных JSON. Он предоставляет двоичное представление разобранного выражения пути SQL/JSON, которое указывает элементы, которые должны быть извлечены из данных JSON для дальнейшей обработки с помощью функций запроса SQL/JSON.

Семантика предикатов и операторов SQL/JSON пути в целом соответствует SQL. В то же время, для обеспечения естественного способа работы с данными JSON, синтаксис SQL/JSON пути использует некоторые соглашения JavaScript:

::: itemizedlist

  • Точка (.{.literal}) используется для доступа к членам.

  • Квадратные скобки ([]{.literal}) используются для доступа к массиву.

  • Массивы SQL/JSON начинаются с 0, в отличие от обычных массивов SQL, которые начинаются с 1. :::

Числовые литералы в выражениях пути SQL/JSON следуют правилам JavaScript, которые в некоторых деталях отличаются как от SQL, так и от JSON. Например, выражение пути SQL/JSON разрешает  .1{.literal} и 1.{.literal}, что недопустимо в JSON. Поддерживаются целочисленные литералы в недесятичном формате и разделители в виде подчеркиваний, например: 1_000_000{.literal}, 0x1EEE_FFFF{.literal}, 0o273{.literal}, 0b100101{.literal}. В выражении пути SQL/JSON (а также в JavaScript, но не в самом SQL) не должно быть разделителя в виде подчеркивания сразу после префикса системы счисления.

Выражение пути SQL/JSON обычно записывается в SQL-запросе как строковый литерал SQL, поэтому оно должно заключаться в одинарные кавычки, а любые внутренние одинарные кавычки в значении необходимо удваивать (см. Раздел 4.1.2.1{.xref}). Некоторые виды выражений пути требуют наличия строковых литералов в их составе. Эти встроенные строковые литералы следуют соглашениям JavaScript/ECMAScript: они должны быть окружены двойными кавычками, и в них могут использоваться экранирования обратной косой чертой для представления символов, которые иначе трудно ввести. В частности, способ записи двойной кавычки внутри встроенного строкового литерала --- это \"{.literal}, а для записи самой обратной косой черты необходимо написать \\{.literal}. Другие специальные последовательности с обратной косой чертой включают те, которые распознаются в строках JavaScript: \b{.literal}, \f{.literal}, \n{.literal}, \r{.literal}, \t{.literal}, \v{.literal} для различных управляющих символов \xNN{.literal} для кода символа, записанного с использованием только двух шестнадцатеричных цифр, \uNNNN{.literal} для символа Unicode, идентифицированного его 4-шестнадцатеричным кодом, и \u{N...{.literal}} для кода символа Unicode, записанного с использованием от 1 до 6 шестнадцатеричных цифр.

Выражение пути состоит из последовательности элементов пути, которые могут быть любыми из следующих:

::: itemizedlist

  • Путь литералов JSON примитивных типов: текст Unicode, числовой, true, false или null.

  • Все переменные пути перечислены в Таблице 8.24{.xref}.

  • Все операторы доступа перечислены в Таблице 8.25{.xref}.

  • jsonpath{.type} операторы и методы перечислены в Разделе 9.16.2.2{.xref}.

  • Круглые скобки, которые можно использовать для задания выражений фильтрации или определения порядка вычисления пути. :::

Для получения подробной информации о использовании выражений jsonpath{.type} с функциями запросов SQL/JSON см. Раздел 9.16.2{.xref}.
